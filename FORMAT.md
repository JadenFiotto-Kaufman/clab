# The clab format

Generated by `clab describe --markdown` from the code; a test fails when this file and the code disagree. A document is one JSON object that declares a complete experiment; `clab run DOC` runs it.

## Root keys

| key | holds |
| --- | --- |
| `description` | what the experiment is, in prose |
| `model` | the checkpoint, and how to load it |
| `data` | each dataset by name |
| `sites` | named locations, referenced by `site` |
| `interventions` | named bundles of entries, pulled into a step's `interventions` by name |
| `featurizers` | named spaces an entry encodes into, and functions it applies |
| `steps` | what runs, in order |
| `saves` | the values that come home, by name |

### `model`

- `key: str`
- `revision: str`
- `dtype: one of "float32", "float16", "bfloat16" = "float32"`

The pinned checkpoint: `key`, `revision` and `dtype` (torch's spelling). Every other key goes to the
engine's loader untouched (`attn_implementation`, ...), and a loader refuses what it cannot honor; where
the model runs (`device`) is a run option, not the document's. The attention interior needs
`attn_implementation: "eager"`.

### `data.<name>`

- `path: str or null = null`
- `rows: list of dict or null = null`
- `split: str or null = null`
- `shuffle: bool = false`
- `take: int or null = null`
- `columns: object of str or null = null`
- `template: object of Any or null = null`

A dataset: where its rows come from and how its text renders, never a computation on its values. `path` is
`data/<path>.json` under the corpus root, or `rows` are inline. Then, in this order: `split` keeps the rows
of a file whose `split` column is that; `shuffle` puts the rows in one fixed random order, the same on every
machine (seed 0); `take` keeps the first N (after `shuffle`, a random sample of N); and `columns` renames
them, `{"<name>": "<column as the source has it>"}`, each name that column and no longer under its own, every
other column as it is (so one file serves a fit's `eval` substitution under the body's column names).
`template` is passed to the checkpoint's `apply_chat_template` wherever a chat column of the dataset renders
(`{"add_generation_prompt": true, "enable_thinking": false}`), so a chat can end in the generation prompt and
keep its `turn` scopes. Refused by name: `take` beyond the rows, a `columns` source the rows lack or a name
that is a column they keep (a swap, `{"a": "b", "b": "a"}`, keeps neither), and a `template` on a dataset no
step reads a chat column of. `sha256` and `n_rows` describe the rows these leave.

### `sites.<name>`, or a `site` inline

- `component: str`
- `layers: selector or a sweep or null = null`
- `select: object of selector or a sweep or null = null`

A component, narrowed: `layers` (a selector, as `pos` has them, of the model's layers: an int is that
layer's value; a slice or a list of picks is one value, a `layers` axis first, labelled with the layers
it picks: `[0, 3, 7]` is three, `"-2:"` the last two) on a block's component, and `select`
(`{<axis>: <selector>}`, which Components describes). A read and a write take `layers` alike: an entry is
made at each layer they pick, in one forward.

### A column read as text

- `column: str`
- `strip: bool = false`
- `lower: bool = false`

A column read as text, where a scope searches for it or a metric scores it: `"<dataset>.<column>"`, or
`{"column": "<dataset>.<column>", "strip"?: bool, "lower"?: bool}` (an indexed input's variables are named
whole: `pairs.counterfactual_inputs_variables[0].entity`). A row's value may be a list of strings: a set, any
of which is the answer. The flags say how its text compares and never rewrite the data: `lower` compares it
lowercased, and `strip` makes its surrounding whitespace optional.

A scope searches the input for the text as the flags compare it, under `strip` without its surrounding
whitespace, its positions the original's.

An answer scored against logits is tokenized as written, and each of its tokens stands for its class: every
token of the vocabulary whose text (what it adds after another token, so a leading space is its own)
compares the same; without a flag, or for a token that is part of a character, the token alone. Under
`strip` the answer's whitespace-only tokens at its end are dropped, since what follows an answer is not
scored; its first token then compares without its leading whitespace and its last without its trailing, a
one-token answer's without either (` Yes`, ` yes`, `yes` and `YES` under both flags); a token between them
compares with its whitespace, and a whitespace-only token, at the start or between, stands for itself
(`" New York "` is `▁New ▁York`, `▁New` standing for `New` too; `" 42"`, on a tokenizer that splits digits,
is `▁ 4 2`, its `▁` itself alone).

### A literal in a list `input`

- `text: str`

`{"text": "<literal>"}`: literal text in a list `input`.

### An entry of `interventions`

- `site: str or site`
- `pos: int or pos or a sweep = {}`
- `ops: list of op = []`

An entry of an `interventions` value: the `site` it lands on (a declared name, or one inline), the
positions `pos` names there (default every token of the prompt, `{"frame": 0, "index": ":"}`), and the `ops` it
runs on that selection, in the order written.

```
step.interventions := item | [item, ...]
item               := "<bundle name>" | {<name>: entry, ...}
entry              := {"site": site, "pos"?: pos, "ops"?: [op, ...]}
root.interventions := {<bundle>: {<name>: entry, ...}}
```

An entry whose ops include an edit (the edits group: `swap`, `add`, `sub`, `scale`, `renormalize`,
`normalize`, `project_out`, `decode`, `apply`, `noise`, `clamp`) writes back: its value after its
last edit replaces the live value at its selection, so later entries and the rest of the forward see it;
one with none leaves the model alone. Every entry binds `<step>.<name>` to its value after all its ops, a
write's included, so what a write wrote is readable. An edit comes before any op that changes the value's
layout (`readout`, a metric, a reduction, an `encode` no `decode` closes): after one there is no live value
to write. An entry's value leaves the model only when something uses it (`saves`, or a later entry or step
names it); an entry nothing names only writes, and costs no memory.

An entry is made at each layer its site's `layers` pick, in one forward: a write at `layers: "2:6"` runs its
ops at each of layers 2 to 5 on that layer's live value, in the forward's order, exactly as four entries
of one layer each (the same ops, in order) would. Every op of the entry runs at each layer, the ops after its
last edit too, and the value it binds stacks what they made there, a `layers` axis first, labelled with the
layers it picks, as a read there does (`[add, readout, token_prob]` at `layers: ":"` is a probability per
layer); so no op inside an entry reduces over `layers`, which a step after the forward does. An operand
meets those layers as Ops says.

A step's entries run in the order written: the items of a list in turn, a dict's entries in turn, a bundle's
where its name stands. Entries at different sites act as the forward reaches their sites; two at one site
compose there in order, each on what the one before it left. A name binds once per step: two entries of one
name are refused. An operand may name an earlier entry of the same forward (`patched.premix` in `patched`),
at this entry's site or at one the forward reaches before it, at each layer this entry is made at: it is that
entry's value in this batch, at its positions, and so an entry whose ops all write (none after its last
edit), in the coordinates the operand meets (`space`). An operand read on another input at the write's own
positions, with no scope, pairs its i-th position with the write's i-th, which on rows whose prompts differ
in length is checked conservatively before any forward: each pair sits at one distance from the start within
the tokens both prompts begin with alike, or from the end within those they end with alike (the first token
past either counted in); any other is refused, and a scope names the token in each row. An operand holds the
indices of every axis a site narrows (`num_heads`, ...) that the value it meets holds, in the same order. A
bundle at the root is a dict of entries pulled into a step by name, a template whose names resolve in the
step that pulls it in: an operand naming one of the bundle's own entries bare (`"with": "premix"`) means that
entry of whichever step pulls it in, and `<a step>.<one of its entries>` is refused, since pulled into
another step it would still mean that step's. An operand from an entry of its own step is served in a
forward; inside a generate it is not yet (a cross-site adapter in a generation is on the roadmap).

### An op in an entry

- `op: str`

An op inside an entry: `{"op": <name>, ...its arguments}` (see Ops).

### `pos`

- `frame: selector or a sweep = 0`
- `scope: scope or null = null`
- `index: selector or a sweep = ":"`

`pos` is three stages of narrowing: `frame` picks forward calls, `scope` picks text within their tokens,
`index` picks positions within that.

**A row's positions are its input tokens, all of them, in order from 0: BOS where the tokenizer adds one,
a chat template's markers, everything but padding, an appended EOS included** (`pos: 0` is BOS where there
is one, `-1` the last token, `{"index": ":"}` every token). Every count of a row's tokens is this one: the
run record's `positions`, `clab table`'s `pos` and `key`, an attention pattern's `key` axis, and a
refusal's token counts.

```
pos      := int                                # shorthand: {"frame": 0, "index": int}
          | {"frame"?: frame, "scope"?: scope, "index"?: selector}     # index default ":"
frame    := selector                                                  # default 0
scope    := {"column": column or a list, "occurrence"?: selector, "before"?: bool}
          | {"text": one or a list, "occurrence"?: selector, "strip"?: bool, "lower"?: bool, "before"?: bool}
          | {"turn": "<role>", "occurrence"?: selector, "before"?: bool}   # occurrence default 0
column   := "<dataset>.<column>" | {"column": "<dataset>.<column>", "strip"?: bool, "lower"?: bool}
selector := int | "<start>:<stop>:<step>" | [int, ...]                # one, a slice, picks
```

Each stage is a selector over what the stage before it left (`selectors.select`): an int counts one
(negative from the last), a slice string is a range in Python notation, half-open, each part optional
(`":"` every one, `"-4:-1"`, `"2:"`, `"::2"`), a list picks those, in the order written. A selector
that picks nothing however many things there are (`"0:0"`, `"5:2"`) is refused, and so is an index that
picks none of the tokens of a frame of a static number of decode calls (`{"frame": "1:3", "index":
"5:"}`).

**frame**: 0 is the prefill, the only call a `forward` step has; k >= 1 is decode call k; a negative k
counts from the row's last call (`-1` is the call that chose its last token, whether that was EOS or the
generation ran to `max_new_tokens`); `"1:"` is every decode call, `":"` the prefill and every decode
call (in a `forward`, its one call: so a named intervention written at `":"` is on in every call of
whichever step names it). A
position is where an input token sits, in a forward and in a generation alike: the prefill holds every
prompt token, its last position the distribution over generated token 0; under the cache decode call k
holds one position, generated token k-1 (its input), and its logits are the distribution over token k. A
row's calls end with the one that chose its last token, so the token it stopped on is never an input. A
generation's prefill computes the head (`lm_head_output`, `logits`) at its last position only, so there
call 0 holds that one position.

**scope** (default: every token the frame selected): `column` and `text` locate text in the selected
calls' tokens, in the prompt by the tokenizer's offsets and in the generated tokens by decoding growing
prefixes: the tokens covering its characters, a chat template's marker among them where the text spans one
(a BOS the tokenizer adds covers none; one a template writes covers its text, `<s>`). An occurrence lies on
token and word boundaries: it starts where a token starts and ends where a token ends (a token's own leading
or trailing whitespace on either side of the boundary; one that ends in the next token's leading whitespace
ends where that token starts, so `Paris. ` does not cover the ` Paris` after it), and where its first or
last character is a letter or a digit, none adjoins it: ` Sara` does not occur in ` Sarah`, ` Ann` not in
` Annabel`, `:` not in `):` (a write found online sees nothing past the token it is fed, so it takes an end
there as a word's, whatever follows). A list of columns or texts locates every occurrence of each.
Occurrences are ordered by where they end, then where they start: where an occurrence becomes known and
where index -1 lands, so a write found online, a read and the run record count them alike (`b` inside `a b
c` comes before it). `occurrence` (default 0, the first of any) picks which of those occurrences among the
tokens the scope is; the scope is the tokens of the picked ones, in order
(their union where occurrences of different texts overlap); `strip` and `lower` (a text's, or on a
column's reference) compare each text stripped of surrounding whitespace and lowercased, the positions
the original's. The prompt and the generated
tokens are searched apart, so a text straddling the boundary is not found; and a row's last generated
token is never an input to any call, so a word ending on it is `alignment_missing` (with
`max_new_tokens: 1` a scope in the generated tokens never matches), unless the scope is `before`.
`turn` is a role of the chat, in call 0 only: its messages are its occurrences, in order (`{"turn":
"user", "occurrence": 1}` is the second user message, `":"` every one of them); a role the row has no
message of is refused by name.

**before** (default false): the positions that predict the scope's tokens, each the position just
before one, the same width: among a frame's calls, the tokens those calls predict are searched, and the
record is the calls' positions whose next token is the scope's. In the prefill that is the position
before each token; in a generation it is the call that chose each generated token, the last one
included (the prefill's last position chose generated token 0). A scope token at position 0 has no
position before it, which makes the row `alignment_missing` (a refusal in the prefill). A write beyond
the prefill lands as its call runs, before the token it would predict is chosen, so it takes no
`before`.

**index** (default `":"`): counts the scope's tokens, over the tokens of every call the frame selected,
in order: `{"frame": "0:3", "index": -1}` is one position, the last token of call 2, the same as
`{"frame": 2, "index": -1}`.

A record has a static width (the same number of positions on every row, `(rows, pos, ...)`) when its frame
names a static number of calls (an int, picks, or a slice with a static width, not `":"` or `"1:"`), its
index has a static width (an int, picks, or a slice whose two ends count from the same side: `"-4:-1"`,
`"-3:"`, `"2:5"`; see `selectors.fixed`), and a `column`/`text` scope, if it has one, is one occurrence in
the prefill; otherwise its rows hold different numbers of positions, and the value is as wide as the widest
row, NaN past a row's own. In the prefill (`frame: 0`) an occurrence a row does not have, or a static index
that does not fit, is refused by name before any forward: the data decided. Anywhere else it is a result, as
is a call the row never reached: the row is `alignment_missing`, NaN all the way.

## Step kinds

Each entry of `steps` is `{"kind": <kind>, ...fields}`.

### `forward`

- `input: str or list of str or literal`
- `interventions: a bundle's name, an object of entry, or a list of them = {}`

One forward over every row of a dataset input. `input` is `<dataset>.<column>` or
`<dataset>.<column>[i]`, a text or a chat, or a list of text columns and `{"text": "<literal>"}`
literals of one dataset, joined per row as they are, with nothing between (`["days.input",
"days.answer"]` appends each row's answer to its prompt: teacher forcing); `interventions` (a bundle's
name, a dict of entries, or a list of either) are what it reads and writes, each entry binding
`<step>.<name>`, in the order written.

A chat input (a list of `{"role", "content"}` messages) is rendered through the checkpoint's own chat
template, given its dataset's `template` as arguments. Without one there is no generation prompt, so the
rendered prompt ends with the template's close of the last message (`[/INST]` on Llama-2-style templates,
`<|im_end|>` and a newline on Qwen3's): `pos: -1` with no scope is that close's last token, a marker or not.
With `{"add_generation_prompt": true}` it ends with the assistant's header, whose tokens are positions like
any other and belong to no `turn`, and a generate from it continues after the header. Either way
`{"scope": {"turn": "user", "occurrence": 1}}` names the second user message's own tokens.

Rows run in consecutive batches of the run's batch size, each padded on the left to the input's longest
row, with position ids that count real tokens. A row's numbers then do not depend on which rows share its
batch, but they do depend on the batch's shape: a trailing partial batch is a smaller matrix, and can
differ in the last bits. Results reproduce to the bit at a fixed batch size.

### `generate`

- `input: str or list of str or literal`
- `interventions: a bundle's name, an object of entry, or a list of them = {}`

Generation from every row of a dataset input. It owns `input` and `interventions`, as a forward does;
every other key goes to the engine's `generate` as-is (`max_new_tokens`, `min_new_tokens`, `do_sample`,
...), and may sweep. Its entries name forward calls by `pos`'s `frame`: the
prefill, and the decode calls, each at its one position. A write at decode call k takes effect from
generated token k on, through the cache. A write lands as its call runs, so beyond the prefill what it
selects is known by then: its frame not counted from the row's last call, and with an
index that names the same calls on a row that stops early as on one that runs on (not one counted from
the end over several calls, nor any but `":"` over the prompt); a frame to the row's last call other than
every decode call (`"2:"`, `"1::2"`) lands at the calls up to the step's `max_new_tokens`, which it then
gives. With a `column` or `text` scope, decode calls only, index -1 and an occurrence counted from the
first. A scoped write is found
online, decoding the inputs fed so far at each call: it lands at the call fed the last token of each
occurrence it picks, as that occurrence appears (its earlier tokens were fed before the text was there
to find), and a row with fewer occurrences than it picks is `alignment_missing`. No write takes a frame
counted from a row's last call. A row's calls are what the engine actually generated, up to the
one that chose the row's first EOS: the step's own `eos_token_id` when it gives one, else the id the
engine's generation stops on (its generation config's). The step's own value is the
new token ids, `[rows, new]`; `detokenize` makes them text. Options that would change the rows or the value
(`num_return_sequences`, `num_beams`, `return_dict_in_generate`, `use_cache`) are refused before anything
runs; any other option is the engine's `generate`'s to accept, and one it rejects fails when the step
runs, naming the step.

Rows run in batches as a forward's do, and reproduce to the bit only at a fixed batch size: the prefill
projects the head at the last position only and every decode call is a `[batch, 1, ...]` matmul, so
batch sizes 4 and 2 already differ by about 1e-7 at call 0.

### `op`

- `op: str`
- `of: str`

An op over a value earlier steps produced: `of` names it, and the op's arguments sit beside it (see
Ops). The step's value is the op's result; a step holds exactly one op, and chaining is the next step.

### `fit`

- `train: list of str`
- `objective: object of float or a sweep`
- `epochs: int or a sweep`
- `batch_size: int or a sweep`
- `seed: int or a sweep`
- `optimizer: optimizer`
- `steps: object of step`
- `early_stop: early_stop or null = null`
- `eval: object of object of str = {}`

Train the featurizers `train` names, inside the run, through the frozen model.

Each trained featurizer is made at the fit's start (drawn from its own `seed`, else the fit's), and the
optimizer over its trainable tensors with it. Each epoch sets a gate's temperature, then runs the body
`steps` over minibatches of `batch_size` rows of its datasets, shuffled by a generator seeded with `seed` and
the epoch, with gradients on and gates soft, and steps the optimizer once per minibatch on the weighted sum
`objective` (`{term: weight}`; a term is a body op averaged over every axis, or a trained featurizer's
scalar, `<featurizer>.<scalar>`). On a model not in float32 a metric term is a float32 loss, as every metric
is (see Ops), so the fit's bundle differs from one trained when metrics computed in the model's dtype.
Gradients are taken for the featurizers' tensors alone; the model's weights are never touched. After each
optimizer step a featurizer with a constraint is projected back onto it (an sae's decoder rows to unit norm).
After each epoch the body runs over every training row in scoring mode (gates hard, no gradients): each body
op's mean and each trained featurizer's scalar is that epoch's entry of `<fit>.history.<op>` and
`<fit>.history.<featurizer>.<scalar>`, and `early_stop` is judged on it. The best epoch's featurizer tensors
(without `early_stop`, the last's) are restored, and the body runs once, scored, per named substitution of
`eval`, in listed order: `{"held_out": {"train": "test"}, "train": {}}` runs it with dataset `train` read as
`test`, then on the data it trained on (a dataset read as another renders its chats with its own `template`,
so the two have the same one). The body's forwards run in batches of `batch_size`, whatever the run's batch
size. `epochs: 0` trains nothing: the featurizers are scored as drawn (an untrained lora is the identity
exactly, a null control), and each history is empty, `[0]`.

The body is a scope of its own that sees every value produced before the fit; a trained featurizer's
name and `<fit>.<featurizer>` both mean the one being trained, and a value with a row per example it uses
is one it makes. Nothing leaves it except through the fit's members: `<fit>.<featurizer>` the trained
featurizer (saved as its bundle), `<fit>.<eval>.<op>` and `<fit>.<eval>.<step>.<entry>` a body value from
the run named `<eval>`, and `<fit>.history.<term>`, `[epochs]`, one entry per epoch run. A sweep over any
of the fit's values (an objective weight, the learning rate) makes the fit, its members and their users a
list of points.

### `fit` blocks

`optimizer`:

- `name: one of "adamw", "adam", "sgd"`
- `lr: float or a sweep`
- `weight_decay: float or a sweep = 0.0`

The fit's optimizer, over the trained featurizers' parameters only.

`early_stop`:

- `metric: str`
- `mode: one of "max", "min"`
- `patience: int or a sweep`

End the fit after `patience` epochs without improvement (`mode` max or min) of body op `metric`'s mean,
scored on the training rows after each epoch.

## Derived fields

Fields a document leaves out, which compile (or, for `run`, the engine) fills:

- `Plan`: `document` (the document file the plan was read from; written relative to its corpus root, where data paths and bundles resolve), `compiled` (whether this is the compiled plan), `sweeps` (each sweep axis by label, in axis order: the paths its sweeps stand at, and their values), `results` (each saved value by name; a swept one is a dict keyed by coordinate), `run` (how the plan ran, set by `execute`)
- `Data`: `sha256` (the digest of the rows, which a re-materialization must match), `n_rows` (how many rows the dataset has)
- `Intervention`: `dims` (the layout of the value the entry binds), `space` (the coordinates that value is in: the encodes its ops leave open, outermost first, each its `featurizer` and `select`; none for the site's own layout), `gathered` (whether the run takes the entry's value off the model: `saves` names it, or a later entry or step uses it)
- `Forward`: `at` (the point's index on each sweep axis it varies over), `dataset` (the dataset whose rows the step's values are aligned to)
- `Generate`: `at` (the point's index on each sweep axis it varies over), `dataset` (the dataset whose rows the step's values are aligned to)
- `OpStep`: `at` (the point's index on each sweep axis it varies over), `dataset` (the dataset whose rows the step's values are aligned to), `dims` (the layout of the step's value)
- `Featurizer`: `at` (the point's index on each sweep axis it varies over), `bundle` (the tensors of the bundle `file_path` names, checked against its header), `header` (the header of the bundle `file_path` names, which preflight checks the model's width against)

## Ops

An op runs in two places, always as the same function:

- as a step, `{"kind": "op", "op": "mean", "of": "harvest.acts"}`, over a value earlier steps produced;
- inside an entry of `interventions`, `"ops": [...]`, on the entry's selection at its site, in order.

Inside an entry an op sees one batch, so it must act per example: one that aggregates over rows is
refused there (make it a step after the forward). An entry's edits act on the live value as the forward
reaches the site, and the value after its last edit is written back; the ops after that run on the value
once it is taken off the model (an entry nothing uses is not taken off, so they do not run).

A row a read beyond the prefill did not reach is missing all the way down, and so is a position past a row's
own where rows hold different numbers of them: NaN, every metric and edit of it NaN, `argmax` and `top_k`
giving it id -1 (`top_k` NaN `probs` or `values` and no token text). Reductions skip it: `mean` is the mean over the
rows and positions that have a value, and `pca` is fitted on them. A featurizer's math sees none of it: a
missing vector goes in as zeros and comes out missing.
An attention pattern's keys past a row's own are missing the same way, NaN, in a read and to a write's ops:
an edit that mixes a vector's entries (`normalize`, `renormalize`, `project_out`) takes the entries that are
there, so a row's own keys are edited as the row has them, and its tail stays NaN; `argmax` and `top_k` over
`key` rank a row's own keys, a vector missing only where it has none.

Ops come in four groups: **metrics** score each example (one number per row and position: `match` is 0 or
1, and the accuracy is a `mean` step after it; `contains` scores a detokenized generation's text);
**reductions** remove axes, by default the rows and positions, a `layers` axis kept (`over` names them;
over `pos`, one value per row); **edits** (`swap`, `add`, `sub`, `scale`, `renormalize`, `normalize`,
`project_out`, `decode`, `apply`, `noise`, `clamp`) keep the value's layout and change its contents, and inside
an entry are what writes back; **transforms** turn each example's value into another of a different layout (logits from
a residual stream, coordinates from a value, tokens from logits, text from ids). An edit comes before any
transform, metric or reduction of its entry, or, after an `encode`, before the `decode` that closes it.

Metrics and the reductions `mean`, `sum` and `min` compute in float32 whatever the model's dtype, and return
float32 (`pca` works in double and returns the value's dtype), so a bfloat16 model's mean, a cosine near 1 or a probability near 1 is not
rounded to its few bits. An edit computes in float32 too, the value and every operand upcast, and rounds once,
to the value's dtype, since an edit writes back; a value read from the model keeps the model's dtype. A rank
(`match`'s most likely token, `argmax`, `top_k`) is the same either way: bfloat16 to float32 is exact. `top_k`
over a vocabulary (`vocab_size`, a probe's `classes`) gives `probs`, a float32 softmax, and over another axis
`values`, the ranked values in the value's own dtype.

A featurizer is reached by three ops. `encode` turns the value into its coordinates in the featurizer's
space (`select: {"features": <selector>}` keeps some of them), `decode` (naming the same featurizer) turns
them back: within an entry each `decode` closes the most recent `encode` not yet closed, which must be of
the same featurizer, and the ops between them act on the coordinates. An operand there is in the same
coordinates (a value read through the same encodes, with the same `select`s, or a number), and one in other
coordinates is refused by name, whatever its width. `decode` writes the change of coordinates back as a
delta, so `[encode x, decode x]` is the identity to the bit, an op that changes no coordinate changes
nothing, and a sparse autoencoder's error term survives; a `select`ed coordinate is scattered back and the
rest gain a change of exactly zero (encoding the result again gives them back to float rounding, about
1e-9, not to the bit). Brackets nest: `[encode a, encode b, <edits>, decode b, decode a]` edits `b`'s
coordinates of `a`'s, `b` as wide as `a`'s coordinates. An entry that writes back with an `encode` still
open, a `decode` with no `encode` open, one of another featurizer than the open one, and an `encode` or
`apply` of a featurizer inside its own `encode`, are refused by name. `apply` is the featurizer's own version
of the value (a subspace's projection, a dictionary's reconstruction without its error term, an adapter's
adapted value): an edit, which writes back. An entry that stops after `encode` reads coordinates.

An op acts at the layers of the value it meets: inside an entry, at each layer the entry is made at in turn; as
a step, at the layers `of`'s `layers` axis is labelled with, or at the one layer a value without that axis was
read at. An operand with a `layers` axis is aligned to them by label: at layer L the op takes the operand's slice
labelled L, whatever order either lists its layers in, so a `kl` step between lenses at `[0, 1, 2]` and
`[2, 1, 0]` pairs layer with layer, and an entry at layer 3 takes slice 3; a layer the op acts at that the
operand does not hold is refused by name before any forward, and so is such an operand where the op acts at no
layer (a model's own value, one reduced over its layers). An operand without a `layers` axis is the same at
every layer, as a direction is.

An argument is filled by a document as its type says: `Value` is a named value or a number (in an edit a named
value of one number, a `mean` over every axis, broadcasts as a number does); `Tokens` a column (a `Column`
reference: the string, or the object with `strip` and `lower`) resolved through the value's own vocabulary, the
tokenizer's against logits or a probe's classes against its scores (a metric scores a `vocab_size` or a `classes`
axis); `Text` a column read as text; `Featurizer` a featurizer's name; anything else is a literal.
`renormalize`'s reference is the value at the site before the step's writes (inside an `encode`, its
coordinates). An operand may name an earlier entry of the same forward, at this entry's site or at one the
forward reaches before it (`patched.premix` in `patched`): it is that entry's value in this batch, at its
positions.

A metric lines an answer up with the read it scores, row by row. Each row's answer is tokenized exactly as
written, without special tokens (`" Friday"` and `"Friday"` are different tokens on most tokenizers), to k
tokens. A column whose every row is one token scores it at every position of its row (a logit lens over
positions). A column with an answer of several tokens lines every row up, one-token rows included: token i
scores the row's position i, so the read carries k positions on that row (a scope with `before` reads the
positions that predict the answer's tokens), and the metric keeps the `pos` axis, NaN past a row's own where
rows' answers differ in length; a `sum`, `min` or `mean` over `pos` makes one number per row of it. A row whose answer and
read do not line up is refused by name, before any forward where the read's positions are the prompt's; and
where the read is a `before` scope on the step's own input (teacher forcing), so is a row whose input's next
token at a position is not one the answer's token there may be. A token stands for its class under the
reference's flags (`Column`). A row's answer may be a set, a list of strings any of which is the answer, its
members one width: at each position the ids any member's token (or class) may be, each once. `match` hits
where the most likely token is any of a position's ids, `token_prob` is their summed probability,
`cross_entropy` minus its log; `token_logit` and `logit_diff` read one id's logit, which several ids have
not, so a class or a set of more than one is refused there. A missing row (a scope the row does not say)
stays missing: NaN.

## Components

The locations clab allows: what each component means, its layout, and what narrows it.

A component's name is nnterp's name for the same value, and its `dims` are
nnterp's layout of it (`batch` first, the token axis named `seq`, or `query` on
an attention pattern). `per_layer` says it is a block's value, so a site names
its `layers`. A site's `select` (`{<axis>: <selector>}`) narrows any axis the table lists as narrowing the
component, as a selector: among that axis's size (the model's `num_heads`, ...) it keeps the indices picked,
in their order, and the axis stays in the layout, so that a site has one layout whatever its selector: an int
keeps one index, an axis of size 1 (`{"num_heads": 3}` is head 3 alone, the same value as `[3]`), where an
int `layers` drops its axis. `key` is each row's own keys, its positions as `pos` counts them (key 0 is BOS
where there is one), so a selector there picks a fixed number of keys counted from the start (`0`, `[0, 2]`,
`"0:3"`); unselected, the axis is as wide as the input's longest row, key j the row's token j, and past a
shorter row's own keys a read is NaN and a write changes nothing (its padding's keys stay as they are).
`stream` marks the residual-stream values `readout` may project.

A selection of a component (what an entry takes, and what its ops see) is
laid out `(rows, pos, *the remaining axes in order)`: a `layers` axis comes
first under `layers` that are a slice or a list of picks, a write's as a read's. A read whose rows hold
different numbers of positions is as wide as its widest row, NaN past a row's own. How an engine reaches a
component is that engine's business; the name says only what the value is.

## Featurizer kinds

Featurizer kinds: the fields each kind takes, what an instance is, and how a value moves in and out of its space.

A featurizer is a space an entry's ops encode into, or a function on a value. Its kind's signature is its
contract: the document fields it takes, with `width` (the feature width of the sites it is used at), `bundle`
and `header` (the tensors and header of the bundle its `file_path` names) supplied by the run, and for a probe
`labels` (its class list). An instance holds plain tensors, never an `nn.Module`, made where the model is: a
declared featurizer before the run's first step, one a fit trains at the fit's start. It is drawn from its
`seed` (else the seed of the fit that trains it, else 0), or loaded from its bundle, which compile reads into
the plan and checks key by key against the document; a loaded one is fixed. Three ops reach it: `encode` gives
its coordinates of a value `h` (the last axis becomes the kind's axis: `features`, or a probe's `classes`),
`decode` writes a change of them back into `h` as a delta (`replace`), so an op between them that changes
nothing changes nothing to the bit, and a sparse autoencoder's error term is kept exactly; and `apply` gives
its version of `h` in `h`'s own layout (a subspace's projection, a dictionary's reconstruction, a gate's
masked value, an adapter's adapted value). A fit trains an instance's `trains` tensors; its objective may name
a featurizer's scalar as `<featurizer>.<scalar>` (a gate's `mask` is the mean of its soft mask; an sae's
`reconstruction` and `l1` are over the coordinates the body read of it in that run of the body, its
`encode`s no `decode` closes, which the instance keeps while a fit trains it). Its math runs on
the value's device and dtype, with autocast off: a model served in bfloat16 under autocast leaves a float32
featurizer's float32 math alone.

A bundle is a safetensors file: an instance's `saves` tensors (the first laid out `[width, ...]`) and a header
saying what made them: the kind and its `header` fields, the model, the site it was used at (`component`, and
`layer`: the one layer, or the list of them, it was made at, counted from the first), its `width` and the
document's name. Both a `pca` op's value and a fit's trained featurizer are saved as one. A document that loads
one is checked against it key by key: the tensors and the kind, its fields and the model when the plan compiles,
the site at every use (each layer it picks one that `layer` names), and `width` against the model's size before
any forward. A file is clab's when its header's `format` is `clab/...`; one that carries clab's header keys under
another format is refused. Any other file is a published one, its kind's to read or refuse: an `sae` reads one
(SAELens, Gemma Scope), whose shapes are checked against each other and the site's width: nothing in it says what
model or site it was made at, so the document states the layer, which every use is checked against.

Each kind is one class, in a module of its own, registered under its name in lower case. It declares as class
attributes what its bundle holds (`saves`), what a fit trains (`trains`), the axis its coordinates are on
(`axis`), the fields its bundle's header records (`header`), the fields one drawn without a `file_path` needs
(`drawn`), the scalars a fit's objective may name (`scalars`) and the fields that count directions of the
value, so are at most its width (`counts`); its constructor makes an instance. The ops it serves are its
methods `encode(h)`, `replace(h, z, new)` (what `decode` runs, so a kind serves `decode` when it has both) and
`apply(h, ...)`, a kind defining only those it has; the rest is the protocol `Kind` declares, with a default for
what a kind need not have.

### `subspace`

- `k: int or null = null`
- `parametrization: one of "cayley" = "cayley"`
- `seed: int or null = null`
- `file_path: str or null = null`

A rank-`k` subspace: the first `k` columns of a rotation `origin @ cayley(theta)`. `origin` is a
Haar-random orthogonal matrix drawn from `seed`, and `theta` (what a fit trains) starts at zero, so an
untrained subspace is a uniformly random one and each seed draws a different one. Its bundle holds the
`[width, k]` basis.

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h` projected onto the subspace.

### `gate`

- `temperature: {start: float, end: float} or null = null`
- `file_path: str or null = null`

A mask over units, `theta` starting at +1 on every one: soft (σ(θ/T)) while a fit trains it, hard
(θ > 0) whenever it is scored. `temperature: {"start", "end"}` sets T, linearly over the fit's epochs
(default 1).

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h` times the mask: soft while a fit trains it, hard when scored.

### `pca`

- `file_path: str`
- `k: int or null = null`

The top-`k` principal directions (`basis`) and the `mean` a `pca` op saved, loaded from its bundle; its
coordinates are centred on the mean.

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h` projected onto the principal directions through the mean: `mean + (h - mean) B Bᵀ`.

### `sae`

- `latents: int or null = null`
- `file_path: str or null = null`
- `seed: int or null = null`
- `activation: one of "relu", "jumprelu", "topk" = "relu"`
- `k: int or null = null`
- `centered: bool = true`
- `site: str or {component: str, layers: int} or null = null`

A sparse autoencoder (`W_enc`, `b_enc`, `W_dec`, `b_dec`), loaded from its bundle, or with `latents` a
dictionary a fit trains: drawn from `seed`, `W_enc` `[width, latents]` standard normal over sqrt(width),
`W_dec` `[latents, width]` with unit-norm rows (kept unit-norm by a projection after each optimizer step),
both biases zero. Its coordinates are the latents `act(pre)`, `pre = (h - b_dec) @ W_enc + b_enc`, or
`h @ W_enc + b_enc` when not `centered` (Gemma Scope's are not), and a `decode` keeps its error term exactly.
`activation` is `relu` (`relu(pre)`), `jumprelu` (`relu(pre) * (pre > threshold)`, with the `threshold` a
published file holds) or `topk` (the relu of the `k` largest of `pre` in each vector, every other latent
zero). Its `file_path` may name a published SAE, a safetensors file with no clab header holding `W_enc`,
`W_dec`, `b_enc`, `b_dec` and optionally `threshold`, as SAELens and Gemma Scope publish them: its shapes
are checked against each other and the site's width, and nothing in it says what model it was trained on, so
the document states what the file cannot: its `activation` and `centered`, which have no default for it, and
the `site` it was trained at (a name from `sites`, or `{"component", "layers"}` with one layer), which every
site it is used at is, component and layer, at each layer the site picks (`layers: -1` counting as the
layer it is). A `site` given for any sae is checked so. Its scalars, over every vector the body read its
coordinates of in that run of the body: `reconstruction`, the mean of ‖h − (z @ W_dec + b_dec)‖², and
`l1`, the mean |z|.

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h`'s reconstruction: the decoding of its latents, `z @ W_dec + b_dec`, without the error term.

### `linear`

- `classes: str`
- `file_path: str or null = null`

A probe, `h @ W + b` (both starting at zero), whose coordinates are its classes: the distinct values of
the `classes` column, sorted, which its bundle's header records. A metric scores them against a column of
those values, as it scores logits against a column of tokens. It has no way back into the value, so it is
read by `encode` and never decoded.

Ops: `encode` gives its coordinates, the last axis becoming classes.

### `lora`

- `rank: int or null = null`
- `alpha: float or null = null`
- `seed: int or null = null`
- `file_path: str or null = null`

A low-rank adapter, `A` `[width, rank]` and `B` `[rank, width]` at scale `alpha / rank`: loaded from its
bundle (its rank and alpha from the bundle's header), or with `rank` and `alpha` one a fit trains, drawn
from `seed`: `A` standard normal over sqrt(width), `B` zero, so it starts as the identity exactly. It has
no coordinates, so its one op is `apply`, and nothing encodes into it.

Ops: `apply`(with: Value or null = null) gives its version of the value, in the value's own layout: `h + (alpha/rank) (x A) B`: `x` is `h`, or `with` (a value at the same positions, from another site of the same forward: an o_proj adapter reads `attention_premix` and applies at `attention_output`), its axes after the positions flattened into the adapter's width. The addition lands on the live value.

## Engines and run options

The engine protocol, and the engines clab ships: `nnterp`, `hooks` and `ndif`.

An engine registers under its name with `@engine("<name>")` and loads its checkpoint in `__init__(model, *,
device="cpu", **options)` from a plan's `model` block: `device` is where it places the model (its one placement
argument, which each engine reads as it likes; `cpu` by default) and `options` are its own keyword parameters,
each with its default and a `<name>: <what it takes>` line in the constructor's docstring, which `clab describe
engines` and FORMAT.md print. `load` refuses an option the engine does not declare, naming the ones it does,
before anything loads; an option the engine cannot honor it refuses by name. It keeps `device` as asked (None
where it does not place the model: an NDIF server does) and `options` as given, after their defaults, which
`execute` records in `plan.run`.

Every engine runs with `batch_size`, how many of a step's rows go through the model in one forward or generation (default 8); the options below are each engine's own.

### `nnterp`

- `device: str = "cpu"`: one torch device ("cpu", "cuda:0") as the loader's device, or "auto", "balanced", ... as its device_map

The primary engine: nnterp's StandardizedTransformer, everything inside one nnsight session.

`device` is one torch device, which nnsight's loader takes as its `device`, or a device map transformers
computes (`auto`, `balanced`, ...), which it takes as its `device_map` and which may spread the model over
several GPUs; the batch's inputs go where the model's first parameter is, and transformers moves them on
from there.

The engine holds its model and nothing else: inside the session the engine and its model are the only
client-side objects, and nnsight ships every name a block closes over to wherever the block runs.

### `hooks`

- `device: str = "cpu"`: one torch device ("cpu", "cuda:0") the model moves to, or "auto", "balanced", ... as its device_map

The second engine: a plain HuggingFace model driven by forward hooks, in this process.

It executes only `AutoModelForCausalLM` (its forward and its `generate`) with
`register_forward_hook` and `register_forward_pre_hook`. nnterp is used once, at load, as a meta shell
(no weights): it says which native module and boundary each component is
(the module whose output or input nnterp's own key for it names), the sizes,
and what the checkpoint supports. A component nnterp reaches inside a
module's forward (`.source`) is not a module boundary, and is refused by name
before anything runs. `device` is one torch device, which the loaded model moves to, or a device map
transformers computes (`auto`, `balanced`, ...), which `from_pretrained` takes as its `device_map` and which
may spread the model over several GPUs; the batch's inputs go where the model's first parameter is, and
transformers moves them on from there.

### `ndif`

- `device: str = "cpu"`: one torch device ("cpu", "cuda:0") where remote "local" places the model; under true, "cpu" alone
- `remote: one of true, "local" = true`: true for the NDIF server nnsight is configured for, "local" for nnsight's in-process simulation of it

The nnterp engine on an NDIF server: the same engine, with a weightless model and a remote session.

It builds nnterp's StandardizedTransformer without dispatching it (a meta shell: the tree, the config and
the tokenizer, no weights; nothing downloads but those) and opens the run's one session with `remote`. The
session body is the nnterp engine's: what ships is the engine (by reference: clab is installed on the server),
the plan (pure data) and the batch size; everything that needs the model, preflight included, runs on the
server, and the results and the run record come home. The server's address and API key are nnsight's own
(`nnsight.CONFIG`, or its environment variables). `remote="local"` runs nnsight's in-process simulation of
that trip, which dispatches the shell here, on `device`, at its first trace.

## Names and scoping

Names are one flat namespace per scope: no dots, and no step also a dataset or a featurizer.

A reference is "thing, then member", split at the first dot: `counterfactual.v_cf` is step
`counterfactual`'s entry `v_cf`; `mean` is an op step's value; `pairs.cf_answer` is a dataset's column; `rot`
is a declared featurizer and `mask.mask` its scalar; `fit.rot` is a fit's member. Values are produced in
document order and referenced only after they exist. A fit's body is a scope of its own: it sees every
value produced before the fit, and nothing leaves it except through `<fit>.<member>`. A bundle of entries
is a template, so the names inside it resolve where a step pulls it in. Under a sweep, a name means the
producer's point that agrees with the consumer's coordinates on the producer's axes. Every value with a
rows axis knows the dataset its rows are aligned to (a forward's input; an op's `of`, operands and
columns), and an op takes one dataset's rows.

## Sweeps

Every `{"sweep": [...], "label"?: "<name>"}` standing for a value, by document path, each with its label:
the `label` it gives, letters, digits and underscores (a coordinate is `<label>=<value>`, joined by commas),
else the name of the field it stands for (the last key of its path). A sweep's values hold no sweep.

A sweep may stand for any value except under `description` and `model`, on a name, a kind, a dataset's
source, or a `file_path`. One label is one axis: sweeps with one label, by default or given, and the same
values are one axis, so their points pair up (zip), as one sweep reached from two places does (a swept site
two steps use); sweeps with one label and different values are refused, and sweeps with different labels
cross. So a read's `layers` swept `{"sweep": [0, 1, 2], "label": "src"}` and a write's `{"sweep": [0, 1, 2],
"label": "dst"}` are a 3×3 grid in one step, each point keyed `src=0,dst=2`; swept `{"sweep": [0, 1, 2]}`
each, both are labelled `layers`, so they pair up, the diagonal, layer L with layer L, and the grid gives one
of them a `label`. A step that uses a swept thing, or references a value that varies, becomes a list of
points, one per combination of its axes, each a whole step whose `at` gives its index on each axis; a step no
sweep touches runs once. A saved value of a swept step is a dict keyed by coordinate: the axis's value, or a
tuple of them in axis order.

## Saves and the output

A run's output directory and back.

One file per save, named after it: `<name>.safetensors` when the value is a tensor or a dict of tensors (a
bundle, `top_k`'s ids and probabilities), `<name>.json` otherwise, tensors in it as nested lists. A swept
save holds one entry per point, keyed by its coordinate, `pos=-1` (`layers=0,pos=-1` over two axes), in
safetensors and JSON alike, a dict's own keys after a `/`. A file is the value and
nothing else, except that a bundle a featurizer loads (the value of an op that declares one, `pca`, and a
fit's trained featurizer) carries the header that featurizer checks; a swept one holds each point's header keys
after its coordinate and a `/`, as its tensors are (`rank=2/rank`), beside one `format`.

`manifest.json` is the compiled plan without the rows it read from files and without bundle tensors, its
`results` each replaced by `{file, step, dims, axes, shape, dtype}`: that is how a result links back to the
step that made it. It records the document's path relative to the corpus root, and each dataset's `n_rows`.
`shape` and `dtype` follow the value's structure (per key, per point). The plan's `run` holds how each input
tokenized, what each generate step's rows generated, and which position (as `pos` counts them: an index into the
row's prompt tokens, BOS first, then its generated ones) every read and write resolved to per row, which
`table` uses to label positions. Values are never in the manifest.

The saved values `names` as rows, joined wide on their shared axes, one column per name.

A value with a rows axis gives a row per example and token: `at` (its point's coordinates; a value whose step is
not swept has no `at`), `row`, `example_id` when the dataset has one, `layer` on a `layers` axis (the model's
layer), the token axes with their tokens (`pos`/`pos_token`, the position a read resolved to, as a document's
`pos` counts them: the index into the row's prompt tokens, BOS first, then in a generation its generated ones,
with the forward `call` holding it for a read in a generation; `key`/`key_token` on an attention pattern,
numbered the same way, the row's own keys only), the dataset columns the step used
(`columns=` to choose), and `value` last: the element, or the remaining axes as nested lists. A row a read
beyond the prefill did not reach gives one row, `alignment_missing` true, with no value; a row's positions
past its own are left out. A value with no rows axis gives a row per element with its axis indices.
