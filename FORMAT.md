# The clab format

Generated by `clab describe --markdown` from the code; a test fails when this file and the code disagree. A document is one JSON object that declares a complete experiment; `clab run DOC` runs it.

## Root keys

| key | holds |
| --- | --- |
| `description` | what the experiment is, in prose |
| `model` | the checkpoint, and how to load it |
| `data` | each dataset by name |
| `sites` | named locations, referenced by `site` |
| `interventions` | named bundles of entries, pulled into a step's `interventions` by name |
| `featurizers` | named spaces an entry encodes into, and functions it applies |
| `steps` | what runs, in order |
| `saves` | the values that come home, by name |

### `model`

- `key: str`
- `revision: str`
- `dtype: one of "float32", "float16", "bfloat16", "nf4", "fp4", "int8", "fp8" = "float32"`

The pinned checkpoint: `key`, `revision` and `dtype`, torch's spelling of a float dtype or one of nnsight's
names for a quantization: `nf4` and `fp4` hold the weights in bitsandbytes' 4 bits (NormalFloat, FloatPoint) and
`int8` in its LLM.int8() 8 bits, on the CPU or on CUDA, with bitsandbytes installed; `fp8` holds them in
transformers' block-wise 8-bit floats, on a GPU of compute capability 8.9 or later. A quantized model computes in
`bfloat16` (`int8` in `float16`), which is the dtype its values have. A key that respells one of the three
(`torch_dtype`, `quantization_config`, `_commit_hash`, ...) or names a run option (`device`, `device_map`:
`--device`; `tp_plan`, ...: `-o tp=N`) is refused by name as the document is read (`plan.OWNED`). Every other
key goes to the engine's loader untouched (`attn_implementation`, ...), which refuses what it cannot honor as
the engine loads, as the load refuses a checkpoint or revision the offline cache lacks. The attention interior
needs `attn_implementation: "eager"`.

### `data.<name>`

- `path: str or null = null`
- `rows: list of dict or null = null`
- `hf: str or null = null`
- `revision: str or null = null`
- `config: str or null = null`
- `split: str or null = null`
- `shuffle: bool = false`
- `skip: int or null = null`
- `take: int or null = null`
- `columns: object of str or derived column or null = null`
- `template: object of Any or null = null`

A dataset: where its rows come from and how its text renders, never a computation on its values. Its rows
come from one of three sources: `path` is `data/<path>.json` under the corpus root, `rows` are inline, and
`hf` is a dataset on the Hugging Face hub, `<owner>/<name>` at `revision` (a commit, as `model` pins one; a
branch is passed as written, and the digest catches what it moves to), in its subset `config` where it has
several. A file's and inline rows travel in the compiled plan; a hub dataset's never do: compile loads them to
check the document and records their digest, and the run loads them again where it runs (under `ndif`, the
server) and refuses other rows before any forward. Then, in this order: `split` picks which split of the
dataset, the hub dataset's split (left out: its only one) or the rows of a file whose `split` column is that;
`shuffle` puts the rows in one fixed random order, the same on every machine (seed 0); `skip` drops the first
N; `take` keeps the first N of the rest (after `shuffle`, a random sample of N; after `skip` too, a shard of
one order: `{"shuffle": true, "skip": 20000, "take": 10000}` is the third of 10,000, so a harvest too large
for one run is made in shards); and `columns` renames them, `{"<name>": "<column as the source has it>"}`,
each name that column and no longer under its own, every other column as it is (so one file serves a fit's
`eval` substitution under the body's column names), or derives one, `{"<name>": {"from": "<column as the
source has it>", ...}}`, text cut from another column's (`Derived`),
which joins the rows and their digest as a column the source has does. `template` is passed to the checkpoint's
`apply_chat_template` wherever a chat column of the dataset renders (`{"add_generation_prompt": true,
"enable_thinking": false}`), so a chat can end in the generation prompt and keep its `turn` scopes; a
checkpoint whose template reads the clock (`strftime_now`: Llama-3.2's writes today's date into the system
header it adds) renders a chat only with its date pinned, `{"date_string": "26 Jul 2024"}`, since the rows'
digest cannot say that the tokens moved with the day. A row is
JSON. Refused by name: a second source, an `hf` that is not `<owner>/<name>`, `hf` without `revision`, and
`revision` or `config` without `hf`; a hub dataset the hub does not give, or offline a commit `revision` other
than the one its cache holds (offline, a branch reads as the cache holds it), a split it does not have (or, of
several, none named), and a column of it whose values are not JSON (images, audio, bytes); a `skip` that
leaves no row, `take` beyond the rows `skip` leaves, a `columns` source the rows lack or a name that is a
column they keep (a swap, `{"a": "b", "b": "a"}`, keeps neither), a `template` on a dataset no step reads a
chat column of, and, before
any forward, a chat of a clock-reading template without `date_string`. `sha256` and `n_rows` describe the rows
these leave.

### A derived column

- `from: str`
- `after: text or null = null`
- `before: text or null = null`
- `strip: bool = false`

`{"from": "<column as the source has it>", "after"?: {"text": ...}, "before"?: {"text": ...}, "strip"?:
bool}`: a column whose text on each row is cut from another's, text on text, decided at compile, never a
computation on its values: the text of column `from` after the first occurrence of `after`'s text, then
before the first occurrence of `before`'s in what is left (each compared exactly), then, under `strip`,
without its surrounding whitespace. `{"from":
"answer", "after": {"text": "#### "}, "strip": true}` is a GSM8K answer's number. `from` stays under its own
name. Refused by name: a row whose `from` is not text, and one on which `after`'s or `before`'s text does not
occur, naming the row.

### `sites.<name>`, or a `site` inline

- `component: str`
- `layers: selector or a sweep or null = null`
- `select: object of selector or key offset or a sweep or null = null`

A component, narrowed: `layers` (a selector, as `pos` has them, of the model's layers: an int is that
layer's value; a slice or a list of picks is one value, a `layers` axis first, labelled with the layers
it picks: `[0, 3, 7]` is three, `"-2:"` the last two) on a block's component, and `select`
(`{<axis>: <selector>}`, which Components describes; on `key`, a selector of keys counted from the start, or
keys relative to each query, `{"offset": k}`, a key offset). A read and a write take `layers` alike: an entry is
made at each layer they pick, in one forward.

### A key relative to the query

- `offset: int or list of int or a sweep`

`{"offset": k}` or `{"offset": [k, ...]}`: on an attention pattern's `key` axis, at each query position p the
entry reads, key p + k of the row's own keys, one per offset in the order written (`{"offset": -1}` the previous
token, `[-1, -2]` the two before it): the axis is as wide as the offsets are many, and an entry is missing (NaN)
where p + k is not one of the row's keys (before its first or past its last). A read's alone: a write selects
keys counted from the start.

### A column read as text

- `column: str`
- `strip: bool = false`
- `lower: bool = false`

A column read as text, where a scope searches for it or a metric scores it: `"<dataset>.<column>"`, or
`{"column": "<dataset>.<column>", "strip"?: bool, "lower"?: bool}` (an indexed input's variables are named
whole: `pairs.counterfactual_inputs_variables[0].entity`). A row's value may be a list of strings: a set, any
of which is the answer. The flags say how its text compares and never rewrite the data: `lower` compares it
lowercased, and `strip` makes its surrounding whitespace optional.

Where an op takes `Tokens` or `Text` (a metric's answer, `contains`'s text), a literal may stand in place of the
column: `{"text": "</think>", "strip"?: bool, "lower"?: bool}`, its text a string or a list of them (a set), the
same on every row of whatever value it goes with, and read exactly as a column holding it on every row is
(tokenized as written, the flags as here). A scope names its text in its own `text` field.

An answer scored against logits is tokenized as written, and each of its tokens stands for its class: every
token of the vocabulary whose text (what it adds after another token, so a leading space is its own) compares
the same; without a flag, or for a token that is part of a character, the token alone. Under `strip`
whitespace-only tokens at the end are dropped, since what follows an answer is not scored, and one at the
start is kept, since a tokenizer that writes a number's space as its own token makes it a token the model
says (`" 42"` is `▁ 4 2`, its `▁` itself alone); the first token then compares without leading whitespace and
the last without trailing, a one-token answer's without either (` Yes`, ` yes`, `yes` and `YES` under both
flags), and one between them keeps its whitespace, a whitespace-only one itself alone (`" New York "` is
`▁New ▁York`, `▁New` standing for `New` too).

### A text

- `text: str`

`{"text": "<text>"}`: a text, written as it is, in a list `input` and as a derived column's `after` or
`before`: one string, its only field (no `strip` or `lower`, and no list, which a literal in an op's argument
takes).

### An entry of `interventions`

- `site: str or site`
- `pos: int or pos or a sweep = {}`
- `ops: list of op = []`

An entry of an `interventions` value: the `site` it lands on (a declared name, or one inline), the
positions `pos` names there (default every token of the prompt, `{"frame": 0, "index": ":"}`), and the `ops` it
runs on that selection, in the order written.

```
step.interventions := item | [item, ...]
item               := "<bundle name>" | {<name>: entry, ...}
entry              := {"site": site, "pos"?: pos, "ops"?: [op, ...]}
root.interventions := {<bundle>: {<name>: entry, ...}}
```

An entry whose ops include an edit (the edits group: `swap`, `add`, `sub`, `scale`, `renormalize`, `normalize`, `project_out`, `decode`, `apply`, `noise`, `clamp`) writes back: its value after its
last edit replaces the live value at its selection, so later entries and the rest of the forward see it;
one with none leaves the model alone. Every entry binds `<step>.<name>` to its value after all its ops, a
write's included, so what a write wrote is readable. An edit comes before any op that changes the value's
layout (`readout`, a metric, a reduction, an `encode` no `decode` closes): after one there is no live value
to write. An entry's value leaves the model only when something uses it (`saves`, or a later entry or step
names it); an entry nothing names only writes, and costs no memory. An entry whose first op is `grad` (see
Ops) writes nothing: its value is a gradient, and every op after `grad`, an edit too, acts on it once it is
off the model.

An entry is made at each layer its site's `layers` pick, in one forward: a write at `layers: "2:6"` runs its
ops at each of layers 2 to 5 on that layer's live value, in the forward's order, exactly as four entries
of one layer each (the same ops, in order) would. Every op of the entry runs at each layer, the ops after its
last edit too, and the value it binds stacks what they made there, a `layers` axis first, labelled with the
layers it picks, as a read there does (`[add, readout, token_prob]` at `layers: ":"` is a probability per
layer); so no op inside an entry reduces over `layers`, which a step after the forward does. An operand
meets those layers as Ops says.

A step's entries run in the order written: the items of a list in turn, a dict's entries in turn, a bundle's
where its name stands. Entries at different sites act as the forward reaches their sites; two at one site
compose there in order, each on what the one before it left. A name binds once per step: two entries of one
name are refused. An operand may name an earlier entry of the same forward (`patched.premix` in `patched`),
at this entry's site or at one the forward reaches before it, at each layer this entry is made at: it is that
entry's value in this batch, at its positions, and so an entry whose ops all write (none after its last
edit), in the coordinates the operand meets (`space`). An operand read on another input at the write's own
positions, with no scope, pairs its i-th position with the write's i-th, which on rows whose prompts differ
in length is checked conservatively before any forward: each pair sits at one distance from the start within
the tokens both prompts begin with alike, or from the end within those they end with alike (the first token
past either counted in); any other is refused, and a scope names the token in each row. What an operand's
layout and labels must be is Ops' one rule. A
bundle at the root is a dict of entries pulled into a step by name, a template whose names resolve in the
step that pulls it in: an operand naming one of the bundle's own entries bare (`"with": "premix"`) means that
entry of whichever step pulls it in, and `<a step>.<one of its entries>` is refused, since pulled into
another step it would still mean that step's. An operand from an entry of its own step is served in a
forward, not inside a generate: a cross-site adapter inside a generate is refused.

### An op in an entry

- `op: str`

An op inside an entry: `{"op": <name>, ...its arguments}` (see Ops).

### `pos`

- `frame: selector or a sweep = 0`
- `scope: scope or null = null`
- `index: selector or a sweep = ":"`

`pos` is three stages of narrowing: `frame` picks forward calls, `scope` picks text within their tokens,
`index` picks positions within that.

**A row's positions are its input tokens, all of them, in order from 0: BOS where the tokenizer adds one,
a chat template's markers, everything but padding, an appended EOS included** (`pos: 0` is BOS where there
is one, `-1` the last token, `{"index": ":"}` every token). Every count of a row's tokens is this one: a
record's `positions`, `clab table`'s `pos` and `key`, an attention pattern's `key` axis, and a
refusal's token counts.

```
pos      := int                                # shorthand: {"frame": 0, "index": int}
          | {"frame"?: frame, "scope"?: scope, "index"?: swept}        # index default ":"
frame    := swept                                                     # default 0
scope    := {"column": column or a list, "occurrence"?: swept, "until"?: bool, "before"?: bool}
          | {"text": one or a list, "occurrence"?: swept, "strip"?: bool, "lower"?: bool, "until"?: bool,
             "before"?: bool}
          | {"turn": "<role>", "occurrence"?: swept, "until"?: bool, "before"?: bool}   # occurrence default 0
column   := "<dataset>.<column>" | {"column": "<dataset>.<column>", "strip"?: bool, "lower"?: bool}
selector := int | "<start>:<stop>:<step>" | [int, ...]                # one, a slice, picks
swept    := selector | {"sweep": [selector, ...]}                     # a point per selector
```

Each stage is a selector over what the stage before it left (`selectors.select`): an int counts one
(negative from the last), a slice string is a range in Python notation, half-open, each part optional
(`":"` every one, `"-4:-1"`, `"2:"`, `"::2"`), a list picks those, in the order written. A selector
that picks nothing however many things there are (`"0:0"`, `"5:2"`) is refused, and so is an index that
picks none of the tokens of a frame of a static number of decode calls (`{"frame": "1:3", "index":
"5:"}`), or whose static width those tokens cannot fill (`{"frame": "1:3", "index": "1:3"}`, two wide over the
one token it picks).

**frame**: 0 is the prefill, the only call a `forward` step has; k >= 1 is decode call k; a negative k
counts from the row's last call (`-1` is the call that chose its last token, whether that was EOS or the
generation ran to `max_new_tokens`); `"1:"` is every decode call, `":"` the prefill and every decode
call (in a `forward`, its one call: so a named intervention written at `":"` is on in every call of
whichever step names it). A
position is where an input token sits, in a forward and in a generation alike: the prefill holds every
prompt token, its last position the distribution over generated token 0; under the cache decode call k
holds one position, generated token k-1 (its input), and its logits are the distribution over token k. A
row's calls end with the one that chose its last token, so the token it stopped on is never an input. A
generation's prefill computes the head (`lm_head_output`, `logits`) at its last position only, so there
call 0 holds that one position.

**scope** (default: every token the frame selected): `column` and `text` locate text in the selected
calls' tokens, in the prompt by the tokenizer's offsets and in the generated tokens by decoding growing
prefixes: the tokens covering its characters, a chat template's marker among them where the text spans one
(a BOS the tokenizer adds covers none; one a template writes covers its text, `<s>`). An occurrence lies on
token and word boundaries: it starts where a token starts and ends where a token ends (a token's own leading
or trailing whitespace on either side of the boundary; one that ends in the next token's leading whitespace
ends where that token starts, so `Paris. ` does not cover the ` Paris` after it), and where its first or
last character is a letter or a digit, none adjoins it: ` Sara` does not occur in ` Sarah`, ` Ann` not in
` Annabel`, `:` not in `):` (a write found online sees nothing past the token it is fed, so it takes an end
there as a word's, whatever follows). A list of columns or texts locates every occurrence of each.
Occurrences are ordered by where they end, then where they start: where an occurrence becomes known and
where index -1 lands, so a write found online, a read and the run record count them alike (`b` inside `a b
c` comes before it). `occurrence` (default 0, the first of any) picks which of those occurrences among the
tokens the scope is; the scope is the tokens of the picked ones, in order
(their union where occurrences of different texts overlap); `strip` and `lower` (a text's, or on a
column's reference) compare each text stripped of surrounding whitespace and lowercased, the positions
the original's. The prompt and the generated
tokens are searched apart, so a text straddling the boundary is not found; and a row's last generated
token is never an input to any call, so a word ending on it is `alignment_missing` (with
`max_new_tokens: 1` a scope in the generated tokens never matches), unless the scope is `before`.
`turn` is a role of the chat, in call 0 only: its messages are its occurrences, in order (`{"turn":
"user", "occurrence": 1}` is the second user message, `":"` every one of them); a role the row has no
message of is refused by name.

**until** (default false): the scope is every token the frame selected up to and including the last token of
the occurrences `occurrence` picks, rather than those occurrences' tokens; on a row that has fewer of them than
it picks (the text never occurs), every token the frame selected, in the prefill too, so nothing is refused
and the record says per row where it ended. So `{"frame": "1:", "scope": {"text": "</think>", "until": true}}`
is each row's generated inputs through its first `</think>`, and `count` of a read there is the thinking's
length in tokens (all its inputs on a row that never closes it). The scope is the frame's: an occurrence that
holds none of the frame's tokens is not one of its own, so over `"2:"` a text said at call 1 is not found and
until is the whole frame, as on a row that never says it. An until scope has no width compile can fix, so it
pairs with no other forward's value. With `before` its frame is decode calls: over a frame that holds the prompt it would start before
the frame's first token (position 0, or at a generation's head the prompt's last, before which its prefill
computes no head) and name no position on any row, so compile refuses it. A write's positions beyond the
prefill are decided call by call, as each runs, and until names positions up to an occurrence not yet seen
then, so a write there takes no until.

**before** (default false): the positions that predict the scope's tokens, each the position just
before one, the same width. The scope is searched among the tokens the frame's calls hold and, where
the frame names the row's last call, the token that call chose (the row's last generated token, which
no call holds); the record is the position before each, which may belong to a call the frame does not
name: under `"frame": "1:"` a word said as generated token 0 is held by decode call 1 and recorded at
the prefill's last position, call 0, which chose it. In the prefill that is the position before each
token; in a generation, the call that chose each generated token, the last one included. A scope token
at position 0 has no position before it, which makes the row `alignment_missing` (a refusal in the
prefill). A write beyond the prefill lands as its call runs, before the token it would predict is
chosen, so it takes no `before`.

**index** (default `":"`): counts the scope's tokens, over the tokens of every call the frame selected,
in order: `{"frame": "0:3", "index": -1}` is one position, the last token of call 2, the same as
`{"frame": 2, "index": -1}`.

A record has a static width (the same number of positions on every row, `(rows, pos, ...)`) when its frame
names a static number of calls (an int, picks, or a slice with a static width, not `":"` or `"1:"`), its
index has a static width (an int, picks, or a slice whose two ends count from the same side: `"-4:-1"`,
`"-3:"`, `"2:5"`; see `selectors.fixed`), and a scope, if it has one, is one occurrence in the prefill and not
`until`; compile writes it. Any other record's width is open at compile, and a prefill record's is the number
every row's positions hold where preflight resolves them and they agree; where rows hold different numbers the
value is as wide as the widest row, NaN past a row's own. Only pairing with another forward's value needs the
width to be one number: compile refuses the pair wherever the `pos` leaves it open, except for a scope of one
occurrence in the prefill, not `until` (the whole scope, or an index of no static width over it), which its rows
decide; where they disagree it is refused by name, with each count's rows, in preflight, or at compile for a
loaded read, which carries its rows' positions. In the prefill (`frame: 0`) an occurrence a row does not have,
or a static index that does not fit, is refused by name before any forward: the data decided. Anywhere else it
is a result, as is a call the row never reached, and as is an index that picks none of a row's tokens (`"5:"`
on a shorter row), in the prefill too: the row is `alignment_missing`, NaN all the way, and a write there is
refused by name, since it has no token to write. So is a later step's write that would take such a value as its
operand on a row it lands on (a read at `{"frame": 3, "index": 0}` on a row whose generation made three calls, or
an op step's value that takes it as any named value: `of`, `with`, a `factor`), which would write NaN there:
refused by name, at compile where the read's frame is a decode call at or past its generation's
`max_new_tokens`, which no row makes, and otherwise in the run, naming the row and the call, a forward's write
before its batch's forward, one at a decode call once the batch's generation says which rows made that call; a
generation in a fit's body records no positions, so a write in the body with such an operand writes NaN there.

## Step kinds

Each entry of `steps` is `{"kind": <kind>, ...fields}`.

### `forward`

- `input: str or list of str or text`
- `interventions: a bundle's name, an object of entry, or a list of them = {}`

One forward over every row of a dataset input. `input` is `<dataset>.<column>` or
`<dataset>.<column>[i]`, a text or a chat, or a list of text columns and texts, `{"text": "<text>"}`,
of one dataset, joined per row as they are, with nothing between (`["days.input",
"days.answer"]` appends each row's answer to its prompt: teacher forcing); `interventions` (a bundle's
name, a dict of entries, or a list of either) are what it reads and writes, each entry binding
`<step>.<name>`, in the order written.

A chat input (a list of `{"role", "content"}` messages) is rendered through the checkpoint's own chat
template, given its dataset's `template` as arguments. Without one there is no generation prompt, so the
rendered prompt ends with the template's close of the last message (`[/INST]` on Llama-2-style templates,
`<|im_end|>` and a newline on Qwen3's): `pos: -1` with no scope is that close's last token, a marker or not.
With `{"add_generation_prompt": true}` it ends with the assistant's header, whose tokens are positions like
any other and belong to no `turn`, and a generate from it continues after the header. Either way
`{"scope": {"turn": "user", "occurrence": 1}}` names the second user message's own tokens.

Rows run in batches of the run's batch size, padded on the left as the run's `padding` says, with position
ids that count real tokens: under `dataset`, the default, consecutive batches each padded to the input's
longest row; under `batch` each padded to its own longest row; under `sorted` the rows longest first, each
batch padded to its own, and every value put back in dataset row order. Padding is never a position, so a
row's `positions` and its `key` axis (as wide as the input's longest row, NaN past the row's own keys) are the
same under each. Under `dataset` a row's numbers depend on the width of the input's longest row, not on which
rows share its batch. At some thread counts the batch's other rows can still move them in the last bits. They
do depend on the batch's shape: a trailing partial batch is a smaller matrix, and a batch padded to its own
width a narrower one. Either can differ in the last bits: in float32 a forward's values move by 6e-8 at most on
the corpus (`tests/test_padding.py`), and a real model's move more. A featurizer trained through such a forward
can move by more than the last bits, since an optimizer such as Adam scales a rounding-sized gradient up to its
step size. So a fit whose trained tensors are compared belongs under `dataset` padding. Results reproduce to the
bit at a fixed batch size, padding, readout and thread count, each of which the run records.

### `generate`

- `input: str or list of str or text`
- `interventions: a bundle's name, an object of entry, or a list of them = {}`

Generation from every row of a dataset input. It owns `input` and `interventions`, as a forward does;
every other key goes to the engine's `generate` as-is (`max_new_tokens`, `min_new_tokens`, `do_sample`,
...), and may sweep. Its entries name forward calls by `pos`'s `frame`: the
prefill, and the decode calls, each at its one position. A write at decode call k takes effect from
generated token k on, through the cache. A write lands as its call runs, so beyond the prefill what it
selects is known by then: its frame not counted from the row's last call, and with an
index that names the same calls on a row that stops early as on one that runs on (not one counted from
the end over several calls, nor any but `":"` over the prompt); a frame to the row's last call other than
every decode call (`"2:"`, `"1::2"`) lands at the calls up to the step's `max_new_tokens`, which it then
gives. With a `column` or `text` scope, decode calls only, index -1 and an occurrence counted from the
first. A scoped write is found
online, decoding the inputs fed so far at each call: it lands at the call fed the last token of each
occurrence it picks, as that occurrence appears (its earlier tokens were fed before the text was there
to find), and a row with fewer occurrences than it picks is `alignment_missing`. A row's calls are what
the engine actually generated, up to the
one that chose the row's first EOS: the step's own `eos_token_id` when it gives one, else the id the
engine's generation stops on (its generation config's). The step's own value is the
new token ids, `[rows, new]`; `detokenize` makes them text. Options that would change the rows, the value or
the calls (`num_return_sequences`, `num_beams`, `return_dict_in_generate`, `use_cache`, `prefill_chunk_size`)
are refused before anything runs; any other option is the engine's `generate`'s to accept, and one it rejects
fails when the step runs, naming the step.

A read beyond the prefill runs the ops after its last edit at each call it reads, on that call's value, up
to the first that is not positionwise (`min`, `max`, `median`, `count`, `match`, `logit_diff`, `token_prob`, `token_logit`, `cross_entropy`, `top_k`, `argmax`, `abs`, `exp`, `log`, `sign`, `sqrt`, `square`, `neg`, `mul`, `div`, `eq`, `ne`, `gt`, `ge`, `lt`, `le` are), removes `pos`, takes an operand with a `pos`
axis or scores an answer of several tokens; those from there on run once the batch's generation ends, on its
calls arranged by position (its record's `per_call` counts those it runs at each call). So a metric of the head at
`{"frame": ":"}` holds one number a call, `[rows, calls]`, where a read with no op, or whose first op waits,
holds `calls × vocab_size` values a row in the model's dtype until the generation ends (twice that while it is
arranged). An op waits where its bits depend on the shape of the value it runs on, as a call's value and the
whole one's differ in shape: a matmul (`readout`'s or an `encode`'s), a sum over a long axis (`kl`'s, `js`'s,
`entropy`'s, `cosine`'s, `mean`'s, `sum`'s, `std`'s, `norm`'s, `dot`'s), and `pow`, which torch computes two
ways. On the CPU either way a value is the same to the bit. On CUDA a per-call metric can differ in its last
bits from the same metric over the whole read, since torch picks a softmax's kernel by the tensor's outer size,
which a call's value and the whole one's differ in.

Rows run in batches as a forward's do, and reproduce to the bit only at a fixed batch size: the prefill
projects the head at the last position only and every decode call is a `[batch, 1, ...]` matmul, so two
batch sizes can differ in the last bits from call 0.

### `op`

- `op: str`
- `of: str`

An op over a value earlier steps produced: `of` names it, and the op's arguments sit beside it (see
Ops). The step's value is the op's result; a step holds exactly one op, and chaining is the next step.

### `fit`

- `train: list of str`
- `objective: object of float or a sweep`
- `epochs: int or a sweep`
- `batch_size: int or a sweep`
- `seed: int or a sweep`
- `optimizer: optimizer`
- `steps: object of step`
- `early_stop: early_stop or null = null`
- `eval: object of object of str = {}`

Train the featurizers `train` names, inside the run, through the frozen model.

Each trained featurizer is made at the fit's start (drawn from its own `seed`, else the fit's), and the
optimizer over its trainable tensors with it. Each epoch sets a gate's temperature, then runs the body
`steps` over minibatches of `batch_size` rows of its datasets, shuffled by a generator seeded with `seed` and
the epoch (a minibatch is its rows' ids in their datasets, so `noise` draws a row's noise in any minibatch
as it does outside the fit), with gradients on and gates soft, and steps the optimizer once per minibatch on
the weighted sum `objective` (`{term: weight}`; a term is a body op averaged over every axis, or a trained
featurizer's scalar, `<featurizer>.<scalar>`). On a model not in float32 a metric term is a float32 loss, as
every metric is (see Ops), so the fit's bundle differs from one trained when metrics computed in the model's
dtype. Gradients are taken for the featurizers' tensors alone; the model's weights are never touched. After each
optimizer step a featurizer with a constraint is projected back onto it (an sae's decoder rows to unit norm).
After each epoch the body runs over every training row in scoring mode (gates hard, no gradients): each body
op's mean and each trained featurizer's scalar the body computes (an sae's only over an encode of it no decode
closes) is that epoch's entry of `<fit>.history.<op>` and `<fit>.history.<featurizer>.<scalar>`, and
`early_stop` is judged on it. The best epoch's featurizer tensors
(without `early_stop`, the last's) are restored, and the fit ends with them scoring (gates hard). Each named
substitution of `eval` is the body once more as ordinary steps after the fit (`evals`), in listed order, each
over every row of its dataset: `{"held_out": {"train": "test"}, "train": {}}` is the body with dataset `train`
read as `test` (its inputs, columns and scopes), then the body over the data it trained on (a dataset read as
another renders its chats with its own `template`, so the two have the same one). The body's forwards, and an
eval's, run in batches of `batch_size`, whatever the run's batch size, padded as the run's `padding` says
(under `sorted`, a minibatch's own rows longest first). `epochs: 0` trains nothing: the featurizers are scored
as drawn (an untrained lora or affine is the identity exactly, a null control), and each history is empty,
`[0]`.

The body is a scope of its own that sees every value produced before the fit; a trained featurizer's name
there is `<fit>.<featurizer>`, the one being trained, which compile writes for its bare name. A value made
before the fit with a row per example of
one of the body's datasets (a harvest) comes into every run of the body at that run's rows, taken by their
ids as the body's datasets are, and as it was made: on its device, in its dtype, with no gradient of its own;
so the model runs while the fit trains only where the body has a forward. The body's datasets are those its
forwards read (with none, the one its harvests are of): a harvest of another is refused, since a minibatch's
ids would pair its rows with theirs. A reduction over rows inside the body is the minibatch's statistic; a
statistic of the dataset is a step before the fit. An eval that reads a harvest's dataset as another is
refused, since no step made the harvest over the other's rows: evaluate on other data in steps after the fit,
through `<fit>.<featurizer>`. So is an objective none of whose terms depends on what the fit trains, which has
no gradient to step on. Nothing leaves the body except through the fit's members: `<fit>.<featurizer>` the
trained featurizer (saved as its bundle), `<fit>.<eval>.<op>` and `<fit>.<eval>.<step>.<entry>` a value of the
eval named `<eval>`, and `<fit>.history.<term>`, `[epochs]`, one entry per epoch run. A sweep over any of the
fit's values (an objective weight, the learning rate) makes the fit, its members and their users a list of
points.

### `fit` blocks

`optimizer`:

- `name: one of "adamw", "adam", "sgd"`
- `lr: float or a sweep`
- `weight_decay: float or a sweep = 0.0`

The fit's optimizer, over the trained featurizers' parameters only.

`early_stop`:

- `metric: str`
- `mode: one of "max", "min"`
- `patience: int or a sweep`

End the fit after `patience` epochs without improvement (`mode` max or min) of body op `metric`'s mean,
scored on the training rows after each epoch.

### `load`

- `from: str`
- `value: str`

A value an earlier run saved, brought into this document with its record: `from` is that run's output
directory under the corpus root (where its `manifest.json` is), `value` a name in its `saves`. The step's value

## Ops

An op runs in two places, always as the same function:

- as a step, `{"kind": "op", "op": "mean", "of": "harvest.acts"}`, over a value earlier steps produced;
- inside an entry of `interventions`, `"ops": [...]`, on the entry's selection at its site, in order.

Inside an entry an op sees one batch, so it must act per example: one that aggregates over rows is
refused there (make it a step after the forward). An entry's edits act on the live value as the forward
reaches the site, and the value after its last edit is written back; the ops after that run on the value
once it is taken off the model (an entry nothing uses is not taken off, so they do not run).

A row a read beyond the prefill did not reach is missing all the way down, and so is a position past a row's own
where rows hold different numbers of them: NaN, every metric, edit and elementwise transform of it NaN, `argmax` and
`top_k` giving it id -1 (`top_k` NaN `probs` or `values` and no token text), and a comparison of it NaN. In ids (an
integer value: `argmax`'s, `top_k`'s `ids`, `expert_indices`) the hole is -1, and it is missing as NaN is: a
comparison, an elementwise transform or a reduction of it is a hole too. Reductions skip it: `mean` is the mean over
the rows and positions that have a value, `count` counts only them, and `pca` is fitted on them. A featurizer's math
sees none of it: a missing vector goes in as zeros and comes out missing (to an elementwise `apply`, a gate's, a
missing element). An attention pattern's keys past a row's own are missing the same way, NaN, in a read and to a
write's ops: an edit that mixes a vector's entries (`normalize`, `renormalize`, `project_out`) takes the entries that
are there, so a row's own keys are edited as the row has them, and its tail stays NaN, as a gate leaves it; `argmax`
and `top_k` over `key` rank a row's own keys, a vector missing only where it has none.

Ops come in four groups: **metrics** score each example (one number per row and position: `match` is 0 or 1, and the
accuracy is a `mean` step after it; `contains` scores a detokenized generation's text); **reductions** remove axes,
by default the rows and positions, a `layers` axis kept (`over` names them; over `pos`, one value per row), `norm`
and `dot` by default `hidden_size`, `count` `pos` and `entropy` (of a softmax) `vocab_size`, else `num_experts`;
**edits** (`swap`, `add`, `sub`, `scale`, `renormalize`, `normalize`, `project_out`, `decode`, `apply`, `noise`, `clamp`) keep the value's layout and change its contents, and inside an entry are what writes
back; **transforms** turn each example's value into another of a different layout (logits from a residual stream,
coordinates from a value, tokens from logits, text from ids), or, `grad`, into its gradient, or of the same one entry
by entry (`abs`, `exp`, `log`, `sign`, `sqrt`, `square`, `neg`, `mul`, `div`, `pow`, and the comparisons `eq`, `ne`,
`gt`, `ge`, `lt`, `le`, 1 where they hold and 0 where not), which, unlike an edit, writes nothing back. An edit comes
before any op of its entry that changes the layout (a transform that does, a metric, a reduction), or, after an
`encode`, before the `decode` that closes it; an elementwise transform may come before an edit, and acts on the live
value that edit writes back (`[{"op": "sign"}, {"op": "scale", "factor": 0.1}]` writes a tenth of each entry's sign).

`grad` is the first op of an entry of a `forward`, and the entry writes nothing: every op after it, an edit too,
acts on the gradient once it is off the model, as the ops after a read's last edit act on the read, so `[{"op":
"grad", "of": "metric"}, {"op": "scale", "factor": "difference"}, {"op": "sum", "over": ["hidden_size"]}]` is
attribution patching's estimate at each row and position; after `grad` no `decode` closes an `encode` and no op
restores the site's value (`renormalize`). The forward takes one backward after its last site for each value its
`grad` entries differentiate, and the model's weights take none. A `grad` in a `generate`, in a fit's body or
under `tp` is refused by name, and so is one whose `of` runs an op no gradient passes through:
`top_k`, `argmax`, `match`, `contains`, `detokenize`, `sign`, `eq`, `ne`, `gt`, `ge`, `lt`, `le`, `count`.

Metrics, every reduction but `pca` and the elementwise arithmetic (`abs` to `pow`) compute in float32 whatever the
model's dtype, and return float32 (`pca` works in double and returns float32 too, a bundle's dtype), so a bfloat16
model's mean, a cosine near 1 or a probability near 1 is not rounded to its few bits. An edit computes in float32
too, the value and every operand upcast, and rounds once, to the value's dtype, since an edit writes back; a value
read from the model keeps the model's dtype. A comparison compares in float32 too and gives its 0 or 1 in the value's
dtype (float32 on ids, where a hole needs a NaN), so `mul` by it (`{"op": "mul", "with": "<a comparison's value>"}`)
masks the value where the comparison fails, and `scale` by it, an edit, writes the masked value back. A rank
(`match`'s most likely token, `argmax`, `top_k`) is the same either way: bfloat16 to float32 is exact. `top_k` over a
vocabulary (`vocab_size`, a probe's `classes`) gives `probs`, a float32 softmax, and over another axis `values`, the
ranked values in the value's own dtype.

A featurizer is reached by three ops. `encode` turns the value into its coordinates in the featurizer's space
(`select: {"features": <selector>}` keeps some of them), `decode` (naming the same featurizer) turns them
back: within an entry each `decode` closes the most recent `encode` not yet closed, which must be of the same
featurizer, and the ops between them act on the coordinates. An operand there is in the same coordinates (a
value read through the same encodes, or turned into them by `encode` steps, with the same `select`s, or a
number), and one in other coordinates is refused by name, whatever its width. `decode` writes the change of
coordinates back as a delta, so `[encode x, decode x]` is the identity to the bit, an op that changes no
coordinate changes nothing, and a sparse autoencoder's error term survives; a `select`ed coordinate is
scattered back and the rest gain a change of exactly zero (encoding the result again gives them back to float
rounding, not to the bit). Brackets nest: `[encode a, encode b, <edits>, decode b, decode a]`
edits `b`'s coordinates of `a`'s, `b` as wide as `a`'s coordinates. An entry that writes back with an `encode`
still open, a `decode` with no `encode` open, one of another featurizer than the open one, and an `encode` or
`apply` of a featurizer inside its own `encode`, are refused by name. `apply` is the featurizer's own version
of the value (a subspace's projection, a dictionary's reconstruction without its error term, an adapter's
adapted value): an edit, which writes back. An entry that stops after `encode` reads coordinates. As a step,
`encode` and `apply` take a read (an entry's value, at its one site; an op's value is refused by name), and
`decode`, the close of an entry's `encode`, is no step.

An operand (a `Value` argument that names a value) meets the value the op acts on at one point: inside an
entry, the entry's selection at each layer the entry is made at in turn (in the coordinates of the encodes open
around the op); as a step, `of`, at the layers its `layers` axis is labelled with, or at the one layer a value
without that axis was read at. One rule says what it may be, and compile refuses the rest by name (preflight,
where a label waits on the model's sizes or the rows' positions): an operand may leave out any axis of the value
it meets, which it then broadcasts over (a singleton axis stands for each where the value has one: a direction
over the rows and positions, a per-row dose over the positions and features, a `[rows, pos]` factor over
`hidden_size`, a per-head scalar over `head_dim`); every axis it has is the value's, in the value's order, with
the same label: `layers` by model layer (a `layers` axis it has covers the layers the op acts at and is aligned
by id: at layer L the op takes its slice labelled L, whatever order either lists its layers in, so a `kl` step
between lenses at `[0, 1, 2]` and `[2, 1, 0]` pairs layer with layer, and an entry at layer 3 takes slice 3; an
op at no layer, on a model's own value or one reduced over its layers, takes no layered operand), `rows` by
dataset (an op takes one dataset's rows, its columns' too), `pos` by the read whose positions both hold, else by
width, as many positions on every row (a read whose rows hold different numbers of positions pairs with no
other read's, but an earlier entry of its own forward, row by row), an axis a site selects (`num_heads`, ...)
by the indices kept, in order (one head does not broadcast over several, and `[1, 4]` would trade places with
`[4, 1]`), `features` by the encodes it is in (the same featurizers and `select`s: an operand inside a bracket
is encoded as the bracket is). A number, or a named value of one number (a `mean` over every axis), broadcasts
in any coordinates. An adapter's input (a lora `apply`'s `with`) is held to its rows and positions alone: its
features are the adapter's width; a gate `apply`'s `with`, the value it interpolates toward, is an operand as
`swap`'s is.

An argument is filled by a document as its type says: `Value` is a named value or a number; `Tokens` a column (a
`Column` reference: the string, or the object with `strip` and `lower`) resolved through the value's own
vocabulary, the tokenizer's against logits or a probe's classes against its scores (a metric scores a
`vocab_size` or a `classes` axis); `Text` a column read as text; either one may be a literal in the column's place,
`{"text": "</think>"}` (with `strip` and `lower` as a column's reference has them, a list a set), read as a column
holding that text on every row is; `Featurizer` a featurizer's name; anything else is the value as written.
`renormalize`'s reference is the value at the site before the step's writes (inside an `encode`, its
coordinates). An operand may name an earlier entry of the same forward, at this entry's site or at one the
forward reaches before it (`patched.premix` in `patched`): it is that entry's value in this batch, at its
positions.

A metric lines an answer up with the read it scores, row by row. Each row's answer is tokenized exactly as
written, without special tokens (`" Friday"` and `"Friday"` are different tokens on most tokenizers), to k
tokens. A column whose every row is one token scores it at every position of its row (a logit lens over
positions). A column with an answer of several tokens lines every row up, one-token rows included: token i
scores the row's position i, so the read carries k positions on that row (a scope with `before` reads the
positions that predict the answer's tokens), and the metric keeps the `pos` axis, NaN past a row's own where
rows' answers differ in length; a `sum`, `min` or `mean` over `pos` makes one number per row of it. A row whose answer and
read do not line up is refused by name, before any forward where the read's positions are the prompt's; and
where the read is a `before` scope on the step's own input (teacher forcing), so is a row whose input's next
token at a position is not one the answer's token there may be. A token stands for its class under the
reference's flags (`Column`). A row's answer may be a set, a list of strings any of which is the answer, its
members one width: at each position the ids any member's token (or class) may be, each once. `match` hits
where the most likely token is any of a position's ids, `token_prob` is their summed probability,
`cross_entropy` minus its log; `token_logit` and `logit_diff` read one id's logit, which several ids have
not, so a class or a set of more than one is refused there. A missing row (a scope the row does not say)
stays missing: NaN.

## Components

The locations clab allows: what each component means, its layout, and what narrows it.

A component's name is nnterp's name for the same value, and the table lists its layout as a selection of it
presents it, `rows, pos` then its own axes in nnterp's order (`COMPONENTS` records nnterp's own layout,
`batch` first and the token axis named `seq`, or `query` on an attention pattern, which is how an engine finds
the token axis). `per_layer` says it is a block's value, so a site names
its `layers`. A site's `select` (`{<axis>: <selector>}`) narrows any axis the table lists as narrowing the
component, as a selector: among that axis's size (the model's `num_heads`, ...) it keeps the indices picked,
in their order, and the axis stays in the layout, so that a site has one layout whatever its selector: an int
keeps one index, an axis of size 1 (`{"num_heads": 3}` is head 3 alone, the same value as `[3]`), where an
int `layers` drops its axis. `key` is each row's own keys, its positions as `pos` counts them (key 0 is BOS
where there is one), so a selector there picks a fixed number of keys counted from the start (`0`, `[0, 2]`,
`"0:3"`), or, in a read, keys relative to each query position, `{"offset": -1}`; unselected, the axis is as
wide as the input's longest row, key j the row's token j, and past a shorter row's own keys a read is NaN and a
write changes nothing (its padding's keys stay as they are).
`stream` marks the residual-stream values `readout` may project. `ids` names the size an integer component's
entries are ids under (`expert_indices`' are experts, under `num_experts`): a write there is a `swap` of ids, each a
whole number from 0 below that size, since the model indexes with them.

A selection of a component, what an entry takes and what its ops see, is laid out as the table lists it, with a
`layers` axis first under `layers` that are a slice or a list of picks, a write's as a read's. A read whose rows hold
different numbers of positions is as wide as its widest row, NaN past a row's own. How an engine reaches a
component is that engine's business; the name says only what the value is.

| `logits` | rows, pos, vocab_size | vocab_size | no | what the model returns, after any softcap |

## Featurizer kinds

Featurizer kinds: the fields each kind takes, what an instance is, and how a value moves in and out of its space.

A featurizer is a space an entry's ops encode into, or a function on a value. Its kind's signature is its
contract: the document fields it takes, with `width` (the feature width of the sites it is used at), `bundle`
and `header` (the tensors and header of the bundle its `file_path` names) supplied by the run, for a probe
`labels` (its class list), and for a featurizer over named axes `kept` (the indices it keeps on each of them: a
gate's units, an affine's layers).
An instance holds plain tensors, never an `nn.Module`, made where the model is: a declared featurizer before the
run's first step (one with a field that names a value, a constant's `init`, once the step that made the value has
run), one a fit trains at the fit's start. It is drawn from its `seed` (else the seed of the fit that
trains it, else 0), or loaded from its bundle, which compile reads into the plan; a loaded one is fixed. Three
ops reach it: `encode` gives
its coordinates of a value `h` (the last axis becomes the kind's axis: `features`, or a probe's `classes`),
`decode` writes a change of them back into `h` as a delta (`replace`), so an op between them that changes
nothing changes nothing to the bit, and a sparse autoencoder's error term is kept exactly; and `apply` gives
its version of `h` in `h`'s own layout (a subspace's projection, a dictionary's reconstruction, a gate's
masked value or, given `with`, its interpolation toward that value, an adapter's adapted value, an affine map's
`h + h W + b`, a pca's projection through its mean, `mean + (h - mean) B Bᵀ`, a constant's vector in place of the
value). A fit's objective may name a featurizer's scalar as `<featurizer>.<scalar>` (a gate's
`mask` is the mean of its soft mask; an sae's `reconstruction` and `l1` are over the coordinates the body read of
it in that run of the body, its `encode`s no `decode` closes, which the instance keeps while a fit trains it). Its
math runs on the value's device and dtype, with autocast off: a model served in bfloat16 under autocast leaves a
float32 featurizer's float32 math alone.

A bundle is a safetensors file: an instance's `saves` tensors (the first laid out `[width, ...]`, but for a featurizer
over axes: a gate's `theta` on the axes it is over, an affine's `W` `[layers, width, width]`) and a header
saying what made them: the kind and its `header` fields, the model, the site it was used at (`component`,
`layer`: the one layer, or the list of them, it was made at, counted from the first, and, where the site
selects, `select`: the indices it kept on each axis it selects, a JSON object), its `width` and the document's
name, and for a gate over named axes the indices it keeps on each of them but `layers` (`kept.<axis>`). Both a
`pca` op's value and a fit's trained featurizer are saved as one. A document that loads one is checked against
it key by key: the tensors (their names, and their shapes against those of one drawn from its header, every
kind's) and the kind, its fields and the model when the plan compiles, the site at every use
(each layer it picks one that `layer` names, its selection the one `select` records, none for a header without
one, which was made at the whole component, and a gate's selection on each axis it is over the one
`kept.<axis>` names), and `width` against the model's size before any forward. A file is clab's when its
header's `format` is `clab/...`; one that carries clab's header keys under another format is refused. Any other
file is a published one, its kind's to read or refuse: an `sae` reads one (SAELens, Gemma Scope).

Each kind is one class, in a module of its own, registered under its name in lower case. It declares as class
attributes what its bundle holds (`saves`), what a fit trains (`trains`), the axis its coordinates are on
(`axis`), the fields its bundle's header records (`header`), the fields one drawn without a `file_path` needs
(`drawn`), what a header field left unstated is where the kind rather than its signature decides it (`unstated`:
an sae's `activation` and `centered`), the scalars a fit's objective may name (`scalars`; those of them over what
the body's encodes of it saw, `over_encodes`, which compile refuses on a body with no open encode of it) and the
fields that count directions of the value, so are at most its width (`counts`), whether its `apply`'s `with` is
its input (`adapts`: an adapter's) or an operand of the value (a gate's), and whether its `apply` is elementwise
(`elementwise`: a gate's), which keeps a missing element of the value missing where any other kind loses its
whole vector, and whether `over` stacks its tensors, one slice per index of the axes it names, its width the
value's last axis (`stacked`: an affine's), or lays its units out on those axes (a gate's); its constructor
makes an instance. The ops it serves are its methods `encode(h)`,
`replace(h, z, new)` (what `decode` runs, so a kind serves `decode` when it has both) and `apply(h, ...)`, a kind
defining only those it has; the rest is the protocol `Kind` declares, with a default for what a kind need not have.

### `subspace`

- `k: int or null = null`
- `parametrization: one of "cayley" = "cayley"`
- `seed: int or null = null`
- `file_path: str or null = null`

A rank-`k` subspace: the first `k` columns of a rotation `origin @ cayley(theta)`. `origin` is a
Haar-random orthogonal matrix drawn from `seed`, and `theta` (what a fit trains) starts at zero, so an
untrained subspace is a uniformly random one and each seed draws a different one. Its bundle holds the
`[width, k]` basis.

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h` projected onto the subspace.

### `gate`

- `over: list of str or null = null`
- `temperature: {start: float, end: float} or null = null`
- `file_path: str or null = null`

A mask over units, `theta` starting at +1 on every one: soft (σ(θ/T)) while a fit trains it, hard
(θ > 0) whenever it is scored. `temperature: {"start", "end"}` sets T, linearly over the fit's epochs
(default 1). The units are the last axis of its site's selection, or with `over` the axes of the selection it
names (`layers` among them where the site picks several), in the selection's order: `theta` is laid out on
them, as many on each as the selection keeps, so `["layers", "num_heads"]` at `attention_premix` over every
layer is one unit per head. That mask meets the value as an operand does under Ops' one rule, broadcast over
the axes it leaves out, its slice of each layer the value is at taken by that layer's id. A gate over axes
serves `apply` alone, since its units are not the last axis an `encode` makes its coordinates. `apply` with
`with` (a value at the same selection, or a number, as `swap`'s) is the interpolation toward it, exact at either
end of the mask. Its `apply` is elementwise, so a missing element of the value stays missing and the rest are
gated (a head gate at `attention_probabilities` on rows of different lengths).

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply`(with: Value or null = null) gives its version of the value, in the value's own layout: `h` times the mask `m`, soft while a fit trains it and hard when scored; with `with`, the interpolation toward it, `h·m + with·(1−m)` while a fit trains it, and when scored `h` where a unit is on and `with` where it is off, each to the bit (a NaN or an infinity on the other side, and a zero's sign, included).

### `pca`

- `file_path: str`
- `k: int or null = null`

The top-`k` principal directions (`basis`) and the `mean` a `pca` op saved, loaded from its bundle; its
coordinates are centred on the mean. A document always loads one (`file_path`); without a bundle it is zeros,
`[width, k]` and `[width]`, the shapes compile holds a loaded bundle to (`uses.check_bundle_shapes`).

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h` projected onto the principal directions through the mean: `mean + (h - mean) B Bᵀ`.

### `sae`

- `latents: int or null = null`
- `file_path: str or null = null`
- `seed: int or null = null`
- `activation: one of "relu", "jumprelu", "topk" or null = null`
- `k: int or null = null`
- `centered: bool or null = null`
- `site: str or {component: str, layers: int} or null = null`

A sparse autoencoder (`W_enc`, `b_enc`, `W_dec`, `b_dec`), loaded from its bundle, or with `latents` a
dictionary a fit trains: drawn from `seed`, `W_enc` `[width, latents]` standard normal over sqrt(width),
`W_dec` `[latents, width]` with unit-norm rows (kept unit-norm by a projection after each optimizer step),
both biases zero. Its coordinates are the latents `act(pre)`, `pre = (h - b_dec) @ W_enc + b_enc`, or
`h @ W_enc + b_enc` when not `centered` (Gemma Scope's are not), and a `decode` keeps its error term exactly.
`activation` is `relu` (`relu(pre)`), `jumprelu` (`relu(pre) * (pre > threshold)`, with the `threshold` a
published file holds) or `topk` (the relu of the `k` largest of `pre` in each vector, every other latent
zero). Left unstated (`null`), `activation` and `centered` are a drawn dictionary's, `relu` and centered,
which its bundle's header records and a document loading a clab bundle is checked against; a published file
has no default for them. Its `file_path` may name a published SAE, a safetensors file with no clab header
holding `W_enc`, `W_dec`, `b_enc`, `b_dec` and optionally `threshold`, as SAELens and Gemma Scope publish
them: its shapes are checked against each other and the site's width, and nothing in it says what model it
was trained on or how it encodes, so the document states what the file cannot: its `activation` and
`centered`, and the `site` it was trained at (a name from `sites`, or `{"component", "layers"}` with one
layer), which every site it is used at is, component and layer, at each layer the site picks (`layers: -1`
counting as the layer it is). A `site` given for any sae is checked so. Its scalars, over every vector the
body read its coordinates of in that run of the body: `reconstruction`, the mean of ‖h − (z @ W_dec +
b_dec)‖², and `l1`, the mean |z|.

Ops: `encode` gives its coordinates, the last axis becoming features; `decode` writes a change of its coordinates back into the value; `apply` gives its version of the value, in the value's own layout: `h`'s reconstruction: the decoding of its latents, `z @ W_dec + b_dec`, without the error term.

### `linear`

- `classes: str`
- `file_path: str or null = null`

A probe, `h @ W + b` (both starting at zero), whose coordinates are its classes: the distinct values of
the `classes` column, sorted, which its bundle's header records. A metric scores them against a column of
those values, as it scores logits against a column of tokens. It has no way back into the value, so it is
read by `encode` and never decoded.

Ops: `encode` gives its coordinates, the last axis becoming classes.

### `lora`

- `rank: int or null = null`
- `alpha: float or null = null`
- `seed: int or null = null`
- `file_path: str or null = null`

A low-rank adapter, `A` `[width, rank]` and `B` `[rank, width]` at scale `alpha / rank`: loaded from its
bundle (its rank and alpha from the bundle's header), or with `rank` and `alpha` one a fit trains, drawn
from `seed`: `A` standard normal over sqrt(width), `B` zero, so it starts as the identity exactly. It has
no coordinates, so its one op is `apply`.

Ops: `apply`(with: Value or null = null) gives its version of the value, in the value's own layout: `h + (alpha/rank) (x A) B`: `x` is `h`, or `with` (a value at the same positions, from another site of the same forward: an o_proj adapter reads `attention_premix` and applies at `attention_output`), its axes after the positions flattened into the adapter's width. The addition lands on the live value.

### `affine`

- `over: list of str or null = null`
- `file_path: str or null = null`

An affine map of the last axis onto itself, `h + h W + b`, `W` `[width, width]` and `b` `[width]`: loaded
from its bundle, or one a fit trains, drawn with both zero, so it starts as the identity exactly and an
`epochs: 0` fit of it is a null to the bit. It draws nothing at random, so it takes no `seed`; it has no
coordinates, so its one op is `apply`, which takes no `with`. With `over: ["layers"]` it holds one map per
layer of its site's selection, `W` `[layers, width, width]` and `b` `[layers, width]`, its width still the
last axis: at each layer the value is at, `apply` takes that layer's map by the layer's id. `over` names
`layers` and no other axis, since a map is a matrix over the last axis. A tuned lens's translators are one
affine over layers.

Ops: `apply` gives its version of the value, in the value's own layout: `h + h W + b`; over layers, with the map of the layer the value is at, by its id, or on a value with a `layers` axis of its own (a step over a read at several layers), each layer's map on that layer's vectors.

### `constant`

- `init: Value or null = null`
- `file_path: str or null = null`

A vector of its site's width, `vector`, which `apply` writes in place of the value at every row and position:
a constant ablation. The vector lies on the site's last axis and is shared across every other axis the site keeps,
so at a site that keeps several heads each takes the same vector; a constant per head is a site per head, each with
a constant of its own. `init` draws it: a number, every entry that number (0 a zero ablation), or the name of a
value that is one vector of the site's width (laid out on the site's last axis alone, in the site's own
coordinates, on no sweep axis, made by a step before the featurizer's first use: a `mean` of a read at the site
over every other axis, a mean ablation), which compile checks and the run passes in where it makes the instance.
A fit trains it from there: drawn as a mean and trained on an objective it is the optimal constant, and at
`epochs: 0`, or untrained outside a fit, it writes `init` itself, to the bit. Loaded, it is its bundle's `vector`,
and `init` beside `file_path` is refused. It has no coordinates, so its one op is `apply`.

Ops: `apply` gives its version of the value, in the value's own layout: `vector` in place of `h`, broadcast over its rows, positions and every axis before its last, in `h`'s dtype and on its device: a copy of the vector, with no arithmetic.

## Engines and run options

The engine protocol, and the engines clab ships: `nnterp`, `hooks`, `ndif` and `vllm`. The nnterp engine's `readout` is the
model's own; the hooks engine's is the standard form (final norm, head, the config's softcap), which agrees on the
corpus (the agreement matrix pins it, tiny Gemma-2's softcap included) and is not promised beyond it.

An engine registers under its name with `@engine("<name>")` and loads its checkpoint in `__init__(model, *,
device="cpu", **options)` from a plan's `model` block: `device` is where it places the model (its one placement
argument, which each engine reads as it likes; `cpu` by default) and `options` are its own keyword parameters,
each with its default and a `<name>: <what it takes>` line in the constructor's docstring, which `clab describe
engines` and FORMAT.md print. `load` refuses an option the engine does not declare, naming the ones it does,
and under torchrun (WORLD_SIZE above 1) an engine without `tp`, each of whose processes would run the whole plan,
before anything loads; an option the engine cannot honor it refuses by name. It keeps `device` as asked (None
where it does not place the model: an NDIF server does) and `options` as given, after their defaults, which
`execute` records in `plan.run`.

Every engine runs with `batch_size`, how many of a step's rows go through the model in one forward or generation (default 8), and `padding`, how each of those batches is padded, recorded beside it in `run` (`--padding`; a fit's minibatches and a generation's batches are padded the same way):

- `dataset`: every batch padded to the longest row of the step's whole input, the default: a row's numbers depend on that width, not on which rows share its batch
- `batch`: each batch padded to its own longest row, the rows in dataset order: fewer tokens fed, and a row's numbers move in the last bits with its batch's width
- `sorted`: a step's rows ordered by token count, longest first, before they are batched, each batch padded to its own longest row, and every value put back in dataset row order before anything reads it: the fewest tokens fed, and numbers that move as under `batch`

and `readout`, how a forward computes the logits it reads, recorded there too (`--readout`):

- `full`: the model's head over every position, the default: a read of `logits` takes the model's own value at the positions it names
- `at-reads`: a forward's reads of `logits` that name fewer than every position are read out from the last block's output at those positions alone, with the engine's `readout`, and the forward stops before the head: the head's compute and memory at the positions read only, and numbers that move in the last bits with the head's shape

The options below are each engine's own.

### `nnterp`

- `device: str = "cpu"`: one torch device ("cpu", "cuda:0") as the loader's device, or "auto", "balanced", ... as its device_map; under tp, "cuda" or "cpu"
- `tp: int = 1`: how many ranks tensor parallelism shards the model over, one process each under `torchrun --nproc-per-node=<tp>`; 1 does not shard it

The primary engine: nnterp's StandardizedTransformer, everything inside one nnsight session.

`device` is one torch device, which nnsight's loader takes as its `device` (and a quantized model's as its
`device_map` too, where it is quantized), or a device map transformers computes (`auto`, `balanced`, ...), which it
takes as its `device_map` and which may spread the model over several GPUs; the batch's inputs go where the model's
first parameter is, and transformers moves them on from there.

`tp` above 1 shards the model by transformers' tensor parallelism instead (`DistributedConfig(tp_size=tp)`, as
nnsight's `distributed_config`), over the `tp` processes torchrun starts, each rank on its own GPU: `torchrun
--nproc-per-node=N --no-python clab run DOC --device cuda -o tp=N` (`--device cpu` where no GPU is visible). Every
rank runs the whole plan, which branches on nothing a rank computes, and samples from a seed rank 0 draws; only
rank 0 writes the output directory and prints, and its run record lists every rank's device. A value the ranks hold
in pieces is refused by name (`split`): the attention's interior but its output projection's input
(`attention_premix`), the MLP's activation, and the output of an embedding the plan shards by vocabulary
(`token_embeddings`, where the checkpoint's plan says `embedding_rowwise`); the residual stream, the attention's
and the MLP's outputs, the head and the logits are whole on every rank. Results under tensor parallelism are not
bit-equal to unsharded ones, since a sharded matmul sums its parts in another order: the ranks agree to the bit, and
agree with `tp` 1 to that rounding, a fit's trained values further: Adam amplifies the rounding (in bfloat16 it can
flip a greedy generation's near-tie token too).

The engine holds its model and its configuration (the sizes it read off the model at load) and nothing else: inside
the session the engine and its model are the only client-side objects, and nnsight ships every name a block closes
over to wherever the block runs.

### `hooks`

- `device: str = "cpu"`: one torch device ("cpu", "cuda:0") the model moves to, or "auto", "balanced", ... as its device_map

The second engine: a plain HuggingFace model driven by forward hooks, in this process.

It executes only `AutoModelForCausalLM` (its forward and its `generate`) with `register_forward_hook` and
`register_forward_pre_hook`. nnterp is used once, at load, as a meta shell: it says which native module and boundary
each component is (the module whose output or input nnterp's key for it names), the sizes, the final norm and head
its `readout` runs in the standard form (not the model's own, as nnterp's is), and what the checkpoint supports,
layer by layer, which this engine refuses by name before anything runs, as well as a value nnterp reads inside a
module's forward (`.source`) or among a module's call arguments (`.inputs`) wherever the module is. A value nnterp
holds flat over tokens at its module (a mixture of experts' routing and routed sum, `[batch * seq, ...]`) is served
as nnterp serves it, `[batch, seq, ...]`. `device` is one torch device, which the loaded model moves to
(a quantized one, which cannot move, loads there), or a device map transformers computes (`auto`, `balanced`, ...),
which `from_pretrained` takes as its `device_map` and may spread over several GPUs; the batch's inputs go where the
model's first parameter is, and transformers moves them on from there.

### `ndif`

- `device: str = "cpu"`: one torch device ("cpu", "cuda:0") where remote "local" places the model; under true, "cpu" alone
- `remote: one of true, "local" = true`: true for the NDIF server nnsight is configured for, "local" for nnsight's in-process simulation of it

The nnterp engine on an NDIF server: the same engine, with a weightless model and a remote session.

It builds nnterp's StandardizedTransformer without dispatching it (a meta shell: the tree, the config and
the tokenizer, no weights; nothing downloads but those) and opens the run's one session with `remote`. The
session body is the nnterp engine's: what ships is the engine (by reference: clab is installed on the server),
the plan (pure data) and the batch size; everything that needs the model, preflight included, runs on the
server, and the results and the run record come home. The server holds the weights and shards the model as its
deployment does, so on a server a quantized `dtype` is refused by name, and the engine takes no `tp`. The server's
address and API key are nnsight's own (`nnsight.CONFIG`, or its environment variables). `remote="local"` runs
nnsight's in-process simulation of that trip. The shell then loads its weights here, on `device`, before the first
step of a run that calls the model (`NnterpEngine.ready`, which `execute` calls before the session opens). Its
forwards stop where the schedule says, under either `remote`, as the nnterp engine's do (on a server, as the clab
installed there says), since the nnsight clab requires leaves no frame of a stopped forward behind. A `load`'s value
travels in the request, inside the plan, as a bundle's tensors do, under either `remote`, so `remote="local"` runs
what a server runs and a server reads no file of the client's; a document whose loads hold more than 512 MiB of
tensors is refused before anything is sent.

### `vllm`

- `device: str = "cuda:0"`: "cuda:0", the first of the GPUs vLLM runs the model on (CUDA_VISIBLE_DEVICES names them), where the run keeps its values; no other
- `tp: int = 1`: how many GPUs vLLM shards the model over (its tensor_parallel_size)
- `memory: float = 0.9`: the fraction of each GPU's memory vLLM reserves for the weights and its cache (its gpu_memory_utilization); the run's own values live outside it
- `max_len: int | None = null`: the longest sequence, prompt and new tokens, the engine serves (its max_model_len); null for the checkpoint's
- `invariant: bool = true`: true runs vLLM's batch-invariant kernels, so that a run reproduces to the bit; false its fastest, whose last bits move between runs

The vLLM engine: nnterp's StandardizedVLLM, every row of a batch its own request inside one trace per batch.

vLLM runs the model in a worker process of its own, where a request's activations are its own tokens, `[tokens,
...]`, with no batch axis and no padding, and where a traced block runs once per request. So this engine takes the
batches `steps.run` hands it as every engine does and executes each batch's bound schedule row by row: one trace per
batch, one invoke per row, carrying the row's own token ids and the half of the bound schedule that is the row's
(`batches.schedule_for_row`). In the worker, `visit_request` visits each site as the nnterp engine's `visited` does,
on the value nnterp serves there (`[1, tokens, ...]`, a private copy) padded on the left to the batch's width, so that
the bound records' indices into the padded batch hold as they are, `batches.visit_site` doing the site's records, and
the value handed back unpadded where a record wrote. Each row's reads come home and are joined along rows (`joined`)
into what the nnterp engine's one forward returns, NaN (-1 in ids) at a decode call a row never made. Nothing is
decided here that the schedule does not say; the model never sees a padding token, so under the batch-invariant
kernels (`invariant`) a row's numbers depend on neither its batch companions nor the run's `padding`.

What vLLM makes different, each refused by name before anything runs, or recorded:

- The head is computed at the last position alone: `logits` (and `lm_head_output`, which nnterp serves as the logits
  where the model does nothing after the head, and refuses naming the softcap or scale where it does) is read or
  written at the prompt's last position only (`last_only`; preflight refuses any other, once the schedule says where
  each record is done).
- The attention pattern and the scores are recomputed from the queries and keys: a read is served, a write is
  refused (`execute`); a read of them beyond the prefill, which compile refuses on every engine, a decode call could
  not serve here either.
- No gradient: a fit is refused in `execute`, a `grad` entry by `steps.start_run` (`gradless`). A quantized `dtype`
  too: vLLM's quantizations are not bitsandbytes' weights. `attn_implementation` in the model block is dropped: vLLM's
  attention backend is its own.
- The engine serves sequences up to its `max_len` (`longest`, vLLM's `max_model_len`): preflight refuses a step whose
  longest row, plus what a generation adds, does not fit, since vLLM would cut the generation short with no EOS.
- A forward runs whole (`stops`): nothing ends a request's forward inside the worker.
- `readout` runs the model's final norm, head and logits processor in the worker (`project_on_vocab`), in a trace of
  its own: the model's own, as the nnterp engine's is. Under `--readout at-reads` it meets the stream alone where
  the forward's final norm fuses it with the last residual add, another kernel, so the two agree to the last bits,
  as `at-reads` promises, not to the bit.
- vLLM's default kernels are not run-to-run stable: two identical request sets differ in the last bits (in bfloat16
  by whole ulps). The engine runs vLLM's batch-invariant kernels (`VLLM_BATCH_INVARIANT`) unless `invariant` is
  false, so that the model's values reproduce to the bit and a null is exact (an entry's own ops after its last edit
  still run per batch on the client's GPU, as on every engine), and has Triton run a float32 matmul in float32
  (`TRITON_F32_DEFAULT=ieee`, where nothing set it), not in TF32 as it would by default. Both are set as the worker
  starts (`ready`), which is when it reads them.
- A generation's options are mapped onto vLLM's sampling (`sampling`), what the step leaves out taken from the
  generation config as transformers takes it, and a row stops on clab's stop ids alone (`ignore_eos`, so that vLLM's
  own EOS does not widen the set); a row's new ids are what vLLM sampled, padded past the row's end with the
  generation config's pad token, as transformers pads.
- The worker's memory is vLLM's: a step's `cost.memory` is None (`nvidia-smi` says), and `cost.tokens` counts the
  batch's padding the model never saw (`real` is what it fed). The run record's `devices` and `dtype` are the
  worker's (the client holds a meta tree), and its `versions` name vLLM's.
- The run's traces are not inside a session (`execute` says why): each batch is one request to vLLM, in plain
  Python, as the hooks engine's calls are.

## Names and scoping

Names are one flat namespace per scope: no dots, and no step also a dataset or a featurizer.

A reference is "thing, then member", split at the first dot: `counterfactual.v_cf` is step
`counterfactual`'s entry `v_cf`; `mean` is an op step's value; `pairs.cf_answer` is a dataset's column; `rot`
is a declared featurizer and `mask.mask` its scalar; `fit.rot` is a fit's member; `top3.ids` is a `top_k` step's
member (`ids`, `probs` or `values`, `tokens`, and over a list of axes `top.ids.rows`, each laid out as the step's
value). Values are produced in
document order and referenced only after they exist. A fit's body is a scope of its own: it sees every
value produced before the fit, and nothing leaves it except through `<fit>.<member>`. A bundle of entries
is a template, so the names inside it resolve where a step pulls it in. Under a sweep, a name means the
producer's point that agrees with the consumer's coordinates on the producer's axes. Every value with a
rows axis knows the dataset its rows are aligned to (a forward's input; an op's `of`, operands and
columns), and an op takes one dataset's rows.

## Sweeps

Every `{"sweep": [...], "label"?: "<name>"}` standing for a value, by document path, each with its label:
the `label` it gives, letters, digits and underscores (a coordinate is `<label>=<value>`, joined by commas),
else the name of the field it stands for (the last key of its path). A sweep's values are numbers, strings,
booleans or lists of them, each point keyed by its value, and hold no sweep: a `pos` sweeps its frame, its index
or a scope's occurrence, not the object.

A sweep may stand for any value except under `description`, `model` and `data` (a dataset's rows are compiled
once, and a step reads them by name), on a name, a kind, a `file_path`, or a featurizer's `over` (a featurizer has
one layout at every point). One label is one axis: sweeps with one label, by default or given, and the same values
pair their points (zip), as one sweep reached from two places does (a swept site two steps use); sweeps with one
label and different values are refused, and sweeps with different labels cross. So a read's `layers` swept
`{"sweep": [0, 1, 2], "label": "src"}` and a write's `{"sweep": [0, 1, 2], "label": "dst"}` are a 3×3 grid in
one step, each point keyed `src=0,dst=2`; swept `{"sweep": [0, 1, 2]}` each, both are labelled `layers`, so they
pair up, the diagonal, layer L with layer L, and the grid gives one of them a `label`. A step that uses a swept
thing, or references a value that varies, becomes a list of points, one per combination of its axes, each a
whole step whose `at` gives its index on each axis; a step no sweep touches runs once.

A value of a swept step depends on some of the step's axes, which its record says (`axes`): the sweeps on its
own entry (its site, its positions, an op's literal argument), those of every value or featurizer its ops
name, and, for an entry of a forward, the forward's own, which are the step's options' and its writes' (each
write's site, positions, ops up to its last edit and their operands; an operand from an earlier entry of the
forward counts that entry's); an op step's value depends on its `of`'s and its operands' axes beside its own
sweeps, and a fit's members on the fit's. So a read of a forward whose writes do not vary depends on its own
sweeps alone, and a generation's ids on the forward's. A value is made once per distinct point on its axes,
and a saved value is a dict keyed by coordinate on those axes (the axis's value, or a tuple of them in axis
order), the value itself where it depends on none; so a read swept over layers beside writes that do not vary
is a dict by layer, and a sampled generation whose points differ in reads alone is one sample. Two points of a
forward or generate step run one forward exactly when they agree on the forward's axes (`schedule`): a sweep
on what a step reads runs one forward, a sweep on what it writes one per point.

## Saves and the output

A run's output directory and back.

One file per save, named after it: `<name>.safetensors` when the value is a tensor or a dict of tensors (a
bundle, `top_k`'s ids and probabilities), `<name>.json` otherwise, tensors in it as nested lists. A swept
save holds one entry per point of the value's own axes (`axes`: those of its step's it depends on), keyed by its
coordinate, `pos=-1` (`layers=0,pos=-1` over two axes), in safetensors and JSON alike, a dict's own keys after a
`/`. A file is the value and
nothing else, except that a bundle a featurizer loads (the value of an op that declares one, `pca`, and a
fit's trained featurizer) carries the header that featurizer checks; a swept one holds each point's header keys
after its coordinate and a `/`, as its tensors are (`rank=2/rank`), beside one `format`.

`manifest.json` is the compiled plan as the run completed it, without the rows it read from files (a hub dataset's
never were there; `table` loads either again, from its file or the hub, and checks it against its `sha256`, as
`dump` does a probe's classes dataset for the header of the bundle it saves) and without bundle tensors, its
`results` each replaced by `{file, step, dims, <its labels>, axes, shape, dtype}`: the value's layout and labels as
its record holds them (`dims`, and those it has of `dataset`, `layers`, `read`, `width`, `kept`, `space`), once
where every point agrees, else per point by coordinate, as `shape` and `dtype` are, and `axes`, the sweep axes the
value depends on, so that a result links back to the step that made it and says what each point of it is. It
records the document's path relative to the corpus root, and each dataset's `n_rows`. The plan's `steps` hold
each record with its labels and, on every read and write, the positions it resolved to per row, which `table` uses
to label positions, and each forward's and generation's `schedule`, which forward served each point and what it
did. The manifest holds each distinct list of positions per row once, in its top-level `positions`, and a record's
`positions` names its list there by index under its dataset (`{"train": 0}`), so records that resolved alike share
one; a record holding its list itself reads as well. The plan's
`featurizers` hold each one's width; its `run` holds the batch size, `padding` and `readout` it ran at (the
padding and the readout even where they are the defaults), the thread count torch computed with (`threads`), the
model's sizes, and what each run of each step cost (`costs`: its seconds, its peak memory on each CUDA device, its
model calls, the tokens they fed, padding included, and of those the rows' own, `real`, and the points it served).
Values are never in the manifest. `tokens.json` beside it is the run's `tokens`, how each input tokenized and what
each generate step's rows generated, a token string per position of every row, which `table` labels positions with:
kept apart, since at many rows they are nearly all of what the manifest would hold, and `load` reads it back
into `run.tokens`.

The saved values `names` as rows, joined wide on the keys they share, one column per name.

A value with a rows axis gives a row per example and token: `at` (its point's coordinates; a value whose step is
not swept has no `at`), `row`, `example_id` when the dataset has one, `layer` on a `layers` axis (the model's
layer), the token axes with their tokens (`pos`/`pos_token`, the position a read resolved to, as a document's
`pos` counts them: the index into the row's prompt tokens, BOS first, then in a generation its generated ones,
with the forward `call` holding it for a read in a generation; `key`/`key_token` on an attention pattern,
numbered the same way, the row's own keys only; a `permute`'s value, whose rows hold other rows' positions, by
plain index), the dataset columns the step used
(`columns=` to choose), and `value` last: the element, or the remaining axes as nested lists. A row a read
did not reach (a call beyond the prefill it never made, a scope it does not say, an index that picks none of
its tokens) gives one row, `alignment_missing` true, with no value; a row's positions past its own are left
out. A value with no rows axis gives a row per element with its axis indices, a `layers` axis by the model's
layer and an axis a `select` keeps by the index kept; a `top_k` over `rows` (alone, or
among a list of axes) a row per pick, its other axes' indices and `k` first, then the ranked value's row at the
pick as its own table labels it, its `value` the ranked value there.

Several values join on the keys they share, the sweep axes by coordinate and the axis columns (`row`, `layer`,
`pos`, `key`; a value with no rows axis its own axes, under the same names), each row of the one with more keys
beside every row of the other that agrees with it on them, an axis one value lacks broadcast over as an operand
broadcasts over an axis it leaves out (an unswept number sits beside every row, a swept one beside every row at
each of its points, a history over `epochs` beside every row at each epoch), the first value's columns first
and the joined `at` both points' coordinates; a shared `pos` or `key` that does not mean one thing for both,
counting the positions of different inputs or a plain index beside a token position, is refused by name.
